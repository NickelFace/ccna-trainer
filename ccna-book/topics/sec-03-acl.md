## Что такое ACL

Упорядоченный список правил «разрешить/запретить», который сравнивается с каждым пакетом
**сверху вниз до первого совпадения**. Что не совпало ни с чем — попадает под невидимый
`deny any` в конце.

Два применения:

- фильтрация транзитного трафика на интерфейсе (`ip access-group`);
- ограничение доступа к самому устройству (`access-class` на vty, привязка к NAT, QoS,
  route-map).

## Стандартные и расширенные

| | Стандартный | Расширенный |
|---|---|---|
| Номера | 1–99, 1300–1999 | 100–199, 2000–2699 |
| Проверяет | только **source IP** | source и destination IP, протокол, порты, флаги |
| Где размещают | **ближе к назначению** | **ближе к источнику** |

Логика размещения: стандартный ACL не знает, куда шёл пакет, поэтому вблизи источника он
отрежет лишнее; расширенный знает всё и должен отбрасывать мусор как можно раньше, чтобы
тот не занимал сеть.

```cfg
! Стандартный: запретить одной подсети, разрешить остальным
access-list 10 deny 192.168.5.0 0.0.0.255
access-list 10 permit any
!
interface GigabitEthernet0/1
 ip access-group 10 out

! Расширенный именованный: HR не ходит к серверу БД, остальное можно
ip access-list extended HR-FILTER
 deny tcp 10.1.5.0 0.0.0.255 host 10.9.9.10 eq 1433
 permit ip any any
!
interface GigabitEthernet0/0
 ip access-group HR-FILTER in
```

Именованные списки предпочтительнее: понятное имя, и строки можно редактировать по
номерам (`no 20`, `15 permit …`) без переписывания всего списка.

## Wildcard-маска

Обратная маска: 0 — бит должен совпасть, 1 — бит безразличен.

| Что описываем | Адрес и wildcard |
|---|---|
| Один хост | `10.1.1.5 0.0.0.0` или `host 10.1.1.5` |
| Подсеть /24 | `10.1.1.0 0.0.0.255` |
| Подсеть /26 | `10.1.1.64 0.0.0.63` |
| Любой адрес | `0.0.0.0 255.255.255.255` или `any` |

Считается вычитанием из 255: маска 255.255.255.192 → wildcard 0.0.0.63.

## Порядок строк решает всё

```cfg
! НЕПРАВИЛЬНО — вторая строка никогда не сработает
access-list 101 permit ip any any
access-list 101 deny tcp any host 10.9.9.10 eq 23

! ПРАВИЛЬНО — сначала частное, потом общее
access-list 101 deny tcp any host 10.9.9.10 eq 23
access-list 101 permit ip any any
```

> [!trap] Ловушка
> Невидимый **`deny any` в конце** каждого ACL — причина «применил список, и всё
> перестало работать». Если задача только запретить одно, нужна явная строка
> `permit ip any any` в конце.

Новые строки в нумерованный список дописываются **в конец** — поэтому «дописал запрет, а
он не сработал» встречается регулярно. В именованном списке строку можно вставить по
номеру последовательности.

## Направление и место применения

`in` — пакеты, **входящие** в интерфейс из сети; `out` — **исходящие** из интерфейса в
сеть. На один интерфейс — **один ACL на протокол и направление**.

Схема рассуждения в задачах:

1. Определи, чей трафик надо остановить (источник) и куда он идёт (назначение).
2. Выбери устройство и интерфейс, через которые он реально проходит.
3. Реши направление: если ACL висит `in` на интерфейсе, куда трафик входит — он не
   попадёт даже в маршрутизацию.
4. Проверь, не отрежет ли правило нужный трафик (обратные пакеты, DNS, DHCP, ICMP).

Пример: «запретить сети 10.1.5.0/24 доступ к серверу 10.9.9.10 по SSH, остальное
разрешить» — расширенный ACL на входном интерфейсе роутера в сети 10.1.5.0/24.

## Проверка

```cli
R1# show access-lists
Extended IP access list HR-FILTER
    10 deny tcp 10.1.5.0 0.0.0.255 host 10.9.9.10 eq 1433 (128 matches)
    20 permit ip any any (54210 matches)

R1# show ip interface gigabitethernet0/0 | include access list
  Outgoing access list is not set
  Inbound  access list is HR-FILTER
```

Счётчик `matches` — главный инструмент отладки: если он не растёт, трафик до правила не
доходит (не тот интерфейс или не то направление).

## ACL для управления устройством

```cfg
access-list 10 permit 10.0.99.0 0.0.0.255
line vty 0 15
 access-class 10 in
```

Так разрешают SSH только с сети управления. Обрати внимание: здесь **стандартный** список
и `access-class`, а не `ip access-group`.

## Разбор задачи: где физически повесить ACL

Топология: `PC (10.1.5.20) — SW1 — R1 (Gi0/0 в 10.1.5.0/24, Gi0/1 в 10.9.9.0/24) — SW2 — SRV
(10.9.9.10)`. Задача: **запретить** сети 10.1.5.0/24 доступ по SSH к серверу 10.9.9.10,
остальной трафик — разрешить.

**Шаг 1 — тип списка.** Нужно фильтровать по source **и** destination, да ещё и по порту —
это возможно только расширенным ACL. Стандартный (видит только source) заставил бы
запретить всей подсети 10.1.5.0/24 вообще всё, а не только SSH к одному серверу.

**Шаг 2 — устройство и интерфейс.** Единственная точка, через которую физически проходит
весь трафик из 10.1.5.0/24 к 10.9.9.10, — это R1. Вопрос в том, на каком именно
интерфейсе и в каком направлении.

**Шаг 3 — направление.** Правило для расширенного ACL — размещать его **как можно ближе к
источнику**, чтобы нежелательный трафик отсекался, не тратя ресурсы сети дальше. Значит:
интерфейс `Gi0/0` (тот, что смотрит в сторону 10.1.5.0/24), направление `in` — трафик
проверяется, как только входит в роутер от PC, и лишний просто не идёт дальше к `Gi0/1`.

```cfg
ip access-list extended BLOCK-SSH-TO-SRV
 deny tcp 10.1.5.0 0.0.0.255 host 10.9.9.10 eq 22
 permit ip any any
!
interface GigabitEthernet0/0
 ip access-group BLOCK-SSH-TO-SRV in
```

**Шаг 4 — проверка побочных эффектов.** Правило `deny` бьёт только по TCP/22 к этому
конкретному хосту — веб, почта и всё остальное из 10.1.5.0/24 (в том числе к самому
серверу 10.9.9.10 на других портах) продолжают работать благодаря `permit ip any any` в
конце списка.

> [!key] Запомнить
> Для расширенного ACL «ближе к источнику» — это конкретно **входной** интерфейс на
> граничном устройстве со стороны источника, а не любой попавшийся порт. Ошибка в выборе
> интерфейса или направления — самая частая причина «ACL написан верно, а не фильтрует».

## Диагностика: ACL пропускает запросы, но клиент не получает ответ

**Симптом.** Расширенный ACL разрешает исходящий SSH-трафик от клиентов к серверу, но
сессии никогда не устанавливаются — клиент видит таймаут, будто сервер недоступен.

**Что смотрим.** Список правил на **обратном** направлении того же интерфейса — если ACL
висит на входе с обеих сторон отдельно, легко забыть, что TCP всегда двунаправленный:

```cli
R1# show access-lists
Extended IP access list OUTBOUND-ALLOW
    10 permit tcp 10.1.5.0 0.0.0.255 host 10.9.9.10 eq 22 (340 matches)

Extended IP access list INBOUND-FILTER
    10 deny tcp any any
    20 permit icmp any any
```

**Что нашли.** На интерфейсе в обратную сторону висит отдельный ACL (`INBOUND-FILTER`),
который блокирует **весь** входящий TCP, включая ответные SYN-ACK от сервера клиенту.
Запрос из 10.1.5.0/24 доходит до сервера (первый ACL его пропускает), а ответ сервера,
приходящий с противоположной стороны, попадает под `deny tcp any any` второго списка и
никогда не возвращается клиенту. Классическая обычная (stateless) ACL **не отслеживает
состояние сессии** — она не знает, что этот TCP-пакет является ответом на уже разрешённый
запрос, и оценивает каждое направление независимо. Решение — либо явно разрешить обратный
трафик (`permit tcp host 10.9.9.10 eq 22 10.1.5.0 0.0.0.255 established`, используя флаг
ACK для грубой имитации состояния), либо использовать zone-based firewall, если нужна
настоящая проверка состояния — тема, выходящая за рамки простого ACL.

> [!trap] Ловушка
> Стандартный ACL сам по себе — не firewall: он не помнит, что происходило с трафиком
> раньше, и каждое направление настраивается **отдельно и независимо**. «Разрешил запросы
> — ответы разрешились сами» — так не работает.

## Разбор: вставка правила в именованный ACL по номеру последовательности

Список уже работает, нужно добавить запрет **перед** существующим разрешающим правилом,
не трогая остальное:

```cli
R1# show access-lists BLOCK-SSH-TO-SRV
Extended IP access list BLOCK-SSH-TO-SRV
    10 deny tcp 10.1.5.0 0.0.0.255 host 10.9.9.10 eq 22
    20 permit ip any any
```

```cfg
ip access-list extended BLOCK-SSH-TO-SRV
 15 deny tcp 10.1.6.0 0.0.0.255 host 10.9.9.10 eq 22
```

Номер `15` физически вставляет новую строку **между** существующими 10 и 20 — именно для
этого нумерация именованных списков по умолчанию идёт с шагом 10, оставляя запас. Если бы
список был **нумерованным** (`access-list 101 ...`), такой трюк был бы недоступен: новые
строки нумерованных списков всегда дописываются в конец, и единственный способ вставить
правило раньше — удалить список целиком и создать заново в нужном порядке (или
редактировать конфигурацию в текстовом виде и залить её целиком).

## Что спрашивают

- «Where should a standard ACL be placed?» — ближе к назначению.
- «What is the wildcard mask for a /26?» — 0.0.0.63.
- «Why did all traffic stop after applying the ACL?» — неявный `deny any` в конце.
- «Which command applies an ACL to an interface?» — `ip access-group <имя|номер> in|out`.
- «Which ACL restricts vty access?» — стандартный список с `access-class`.
- «Refer to the exhibit… will this packet be permitted?» — идти по строкам сверху вниз до
  первого совпадения.
- «An extended ACL must block traffic from a specific subnet to one server on one port.
  Where is the best interface and direction to apply it?» — как можно ближе к источнику,
  на входящем (`in`) интерфейсе граничного устройства со стороны этой подсети.
- «Return traffic from an allowed session never reaches the client, even though outbound
  requests are permitted. Why?» — ACL stateless: обратное направление фильтруется
  отдельным списком, который не знает, что трафик — ответ на уже разрешённый запрос;
  нужен явный `permit ... established` или проверка состояния через firewall.
- «How can a rule be inserted between two existing lines of a named ACL without
  recreating it?» — командой с номером последовательности между существующими (например,
  15 между 10 и 20); в нумерованных списках так нельзя — там строки всегда идут в конец.

## Проверь себя

```check
?? Пакет не совпал ни с одной строкой ACL. Что с ним будет?
!! Он будет отброшен неявным deny any в конце списка.
?? Стандартный ACL ставят ближе к источнику или к назначению и почему?
!! К назначению: он видит только адрес источника и вблизи источника отрезал бы лишнее.
?? Какая wildcard-маска описывает ровно один хост?
!! 0.0.0.0 (или ключевое слово host).
?? Дописали deny в конец нумерованного ACL, но запрет не работает. Почему?
!! Строка добавилась после permit ip any any — до неё дело не доходит; нужен именованный список и вставка по номеру.
?? Какой командой ограничивают SSH к устройству по адресам источника?
!! access-class на линиях vty со стандартным ACL.
?? Нужно запретить одной подсети SSH к одному серверу, остальное разрешить. На каком интерфейсе и в каком направлении вешать расширенный ACL?
!! На входящем интерфейсе граничного устройства со стороны этой подсети (in) — как можно ближе к источнику, чтобы лишний трафик не шёл дальше в сеть.
?? Исходящие SSH-запросы разрешены ACL, но ответы от сервера до клиента не доходят. В чём причина?
!! ACL не хранит состояние — обратное направление фильтруется отдельным списком, который блокирует входящий TCP как обычный, не узнавая в нём ответ на уже пропущенный запрос.
?? Как вставить правило между 10-й и 20-й строками именованного ACL, не переписывая его целиком?
!! Задать новой строке номер последовательности между ними, например 15 — в именованных списках это работает; в нумерованных строки всегда добавляются в конец.
```
