## Что такое таблица маршрутизации

Это список известных роутеру сетей и способ до каждой добраться. Всё, что роутер делает с
пакетом, — ищет в этой таблице **самый длинный совпадающий префикс** и отправляет пакет
next hop-у.

```cli
R1# show ip route
Codes: L - local, C - connected, S - static, R - RIP, M - mobile, B - BGP
       D - EIGRP, EX - EIGRP external, O - OSPF, IA - OSPF inter area
       * - candidate default

Gateway of last resort is 10.10.10.18 to network 0.0.0.0

S*    0.0.0.0/0 [1/0] via 10.10.10.18
      10.0.0.0/8 is variably subnetted, 4 subnets, 4 masks
C        10.10.10.0/30 is directly connected, FastEthernet0/1
L        10.10.10.2/32 is directly connected, FastEthernet0/1
O        10.10.13.0/25 [110/6576] via 10.10.10.1, 06:58:21, FastEthernet0/1
D        10.10.20.0/24 [90/2172416] via 10.10.10.1, 00:12:03, FastEthernet0/1
S        192.168.5.0/24 [1/0] via 10.10.10.6
```

Разбор строки `O 10.10.13.0/25 [110/6576] via 10.10.10.1, 06:58:21, FastEthernet0/1`:

| Часть | Что означает |
|---|---|
| `O` | источник маршрута — OSPF |
| `10.10.13.0/25` | сеть и её префикс |
| `110` | **административная дистанция** |
| `6576` | **метрика** протокола |
| `via 10.10.10.1` | next hop |
| `06:58:21` | сколько маршрут живёт в таблице |
| `FastEthernet0/1` | исходящий интерфейс |

## Коды источников

| Код | Источник |
|---|---|
| `C` | connected — сеть на поднятом интерфейсе |
| `L` | local — /32 адрес самого интерфейса |
| `S` | static |
| `S*` | static default route |
| `O`, `IA`, `E1/E2` | OSPF: внутризонный, межзонный, внешний |
| `D`, `EX` | EIGRP: внутренний, внешний |
| `R` | RIP |
| `B` | BGP |

**C и L появляются парой**: `C` — вся подсеть интерфейса, `L` — сам адрес интерфейса
как /32. Условие появления обоих: интерфейс в состоянии up/up **и** у него есть адрес.
Погас интерфейс — обе записи исчезли, а вместе с ними и всё, что через него шло.

## Административная дистанция: чему верить

AD — «доверие к источнику». Если один и тот же префикс пришёл от двух протоколов, в
таблицу попадёт маршрут с **меньшей AD**.

| Источник | AD |
|---|---:|
| Connected | 0 |
| Static | 1 |
| eBGP | 20 |
| EIGRP (internal) | 90 |
| OSPF | 110 |
| IS-IS | 115 |
| RIP | 120 |
| EIGRP (external) | 170 |
| iBGP | 200 |
| Unusable (маршрут не будет использован) | 255 |

Эту таблицу спрашивают в лоб, а также косвенно: «маршрут пришёл и по OSPF, и по EIGRP —
какой попадёт в таблицу» → EIGRP (90 < 110).

## Метрика: выбор внутри одного протокола

Метрика сравнивается **только между маршрутами одного протокола**:

| Протокол | Метрика |
|---|---|
| RIP | число хопов |
| OSPF | стоимость (cost), обратно пропорциональна полосе |
| EIGRP | композитная: полоса и задержка (по умолчанию) |
| BGP | не метрика, а набор атрибутов (AS-path и другие) |

Сравнивать метрику OSPF с метрикой EIGRP бессмысленно — они в разных единицах, для этого и
существует AD.

## Порядок выбора маршрута

Когда пакет приходит, роутер выбирает так:

1. **Самый длинный совпадающий префикс** — это главный и первый критерий. Маршрут /32
   всегда победит /24, даже если у /24 меньше AD.
2. Если префикс одинаковый — **меньшая AD**.
3. Если и AD одинаковая (один протокол) — **меньшая метрика**.
4. Если всё одинаково — балансировка **equal-cost**, до 4 путей по умолчанию.

> [!key] Запомнить
> Порядок именно такой: **префикс → AD → метрика**. Вопрос «пакет к 10.1.1.5, в таблице
> есть 10.0.0.0/8 по EIGRP и 10.1.1.0/24 по RIP — куда пойдёт» решается на первом шаге:
> по /24, несмотря на худшую AD у RIP.

## Gateway of last resort

Маршрут по умолчанию `0.0.0.0/0` — «всё остальное туда». В выводе он отмечен как
`S*` (статический кандидат) или приходит от протокола маршрутизации. Строка `Gateway of
last resort is …` вверху вывода — то, что читают в первую очередь в вопросах «куда уйдёт
пакет к неизвестной сети».

Если её нет (`Gateway of last resort is not set`), пакет к неизвестной сети **просто
отбрасывается**, а отправителю уходит ICMP Destination Unreachable.

## Типы маршрутов по назначению

- **Network route** — обычная сеть с маской короче /32 (`10.1.1.0/24`).
- **Host route** — `/32`, ровно один адрес. Появляется как `L` для своих интерфейсов, а
  также при явной настройке или от протоколов (например, loopback соседа).
- **Default route** — `0.0.0.0/0`.
- **Floating static** — статический маршрут с искусственно повышенной AD, чтобы он ждал
  в стороне и включался только при отказе основного.

## Полезные команды

```cli
R1# show ip route 10.10.13.7          ! какой маршрут выберется именно для этого адреса
Routing entry for 10.10.13.0/25
  Known via "ospf 1", distance 110, metric 6576

R1# show ip route ospf                ! только маршруты одного протокола
R1# show ip route | include 192.168    ! фильтр по строке
R1# show ip cef 10.10.13.7            ! что реально в таблице пересылки
```

`show ip route <адрес>` — самый прямой способ ответить на вопрос «через что пойдёт пакет»:
роутер сам выполняет longest prefix match.

## Разбор задачи: longest prefix match среди трёх похожих маршрутов

Таблица содержит три маршрута к перекрывающимся сетям:

```txt
   10.1.0.0/16    via R2
   10.1.4.0/22    via R3
   10.1.4.0/24    via R4
```

Пакет идёт к `10.1.4.55`. Проверяем каждый маршрут отдельно, а не «на глаз похожий»:

```txt
   10.1.4.55  = 00001010.00000001.00000100.00110111
   /16 маска совпадает с 10.1.0.0    — да, первые 16 бит совпадают
   /22 маска совпадает с 10.1.4.0    — да, первые 22 бита совпадают
   /24 маска совпадает с 10.1.4.0    — да, первые 24 бита совпадают
```

Все три маршрута формально покрывают адрес назначения — это нормально, в таблице
одновременно живут более общий и более точный маршрут к пересекающимся диапазонам. Роутер
выбирает **самый длинный** из подходящих префиксов: `/24` длиннее `/22`, а тот длиннее
`/16`. Ответ — маршрут через **R4**, и AD/метрика здесь вообще не участвуют в решении,
потому что до сравнения AD дело не дошло: критерий длины префикса решил вопрос раньше.

> [!trap] Ловушка
> Наличие в таблице более широкого маршрута (`/16`) с меньшей AD, чем у узкого (`/24`), не
> имеет значения. Длина префикса всегда проверяется первой, AD — только при равенстве
> длины префикса между разными протоколами.

## Диагностика: резервный маршрут не подхватывается при отказе основного

**Симптом.** Настроили floating static как резерв на случай отказа основного канала, но
после обрыва основного трафик всё равно не идёт через резервный.

**Что смотрим.** Саму запись маршрута до сбоя и после:

```cli
R1# show ip route 192.168.50.0
Routing entry for 192.168.50.0/24
  Known via "static", distance 5, metric 0
  Routing Descriptor Blocks:
  * 10.10.10.6, via GigabitEthernet0/2
```

**Что нашли.** AD резервного маршрута выставлена в 5 — это меньше, чем у основного, если
основной пришёл, например, по OSPF (110). Работает это наоборот тому, что задумывалось:
резервный маршрут с AD **ниже**, чем у основного, будет побеждать **всегда**, а не только
при отказе — то есть он не резервный, а основной. Правильная floating static нарочно
делается с AD **выше**, чем у маршрута, который она должна подстраховывать (например, 5
для основного OSPF с AD 110 нужно заменить на что-то вроде 115): пока основной маршрут
жив, в таблицу выбирается он, а floating static сидит рассчитанной, но неактивной, и
попадает в таблицу, только когда основной пропадает целиком.

```cfg
ip route 192.168.50.0 255.255.255.0 10.10.10.6 115
```

> [!key] Запомнить
> Floating static работает только если её AD **выше** AD основного маршрута. Меньшая AD —
> частая ошибка конфигурации, из-за которой «резервный» маршрут внезапно становится
> постоянным основным.

## Диагностика: маршрут в таблице есть, а пакеты не идут

**Симптом.** `show ip route 10.10.13.7` показывает корректный маршрут через next hop
`10.10.10.1`, но пинг до адреса назначения не проходит.

**Что смотрим.** Соответствие RIB и FIB (см. главу про модели OSI — те же понятия) и
доступность самого next hop:

```cli
R1# show ip route 10.10.13.7
Routing entry for 10.10.13.0/25
  Known via "ospf 1", distance 110, metric 6576
  * 10.10.10.1, via FastEthernet0/1

R1# show ip cef 10.10.13.7
10.10.13.0/25   receive
```

**Что нашли.** Маршрут числится в RIB, но `show ip cef` показывает `receive` или
`no route` вместо реального next hop — расхождение между таблицей маршрутизации и
таблицей пересылки. Практическая причина почти всегда одна: **next hop `10.10.10.1`
недостижим на канальном уровне** — ARP до него не разрешился (нет записи в
`show ip arp`), интерфейс к нему упал, либо next hop сам не отвечает. Маршрут остаётся в
RIB, пока протокол маршрутизации не сообщит об исчезновении сети, а вот в FIB запись без
рабочей L2-смежности не соберётся. Экзаменационный вывод: «маршрут в таблице есть, а
трафик не идёт» проверяют не переконфигурацией маршрутизации, а доступностью next hop —
ARP, интерфейс, встречная сторона линка.

## Что спрашивают

- «Which route will be used to reach host X?» — longest prefix match по выводу.
- «What is the administrative distance of OSPF / EIGRP / static?» — 110 / 90 / 1.
- «Which two values are shown in brackets?» — AD и метрика.
- «What does the L entry represent?» — локальный /32 адрес интерфейса.
- «Which type of route does R1 use to reach host 10.10.13.10/32?» — по префиксу в выводе:
  если совпал /25, это network route, а не host route.
- «What happens if there is no default route and the destination is unknown?» — пакет
  отбрасывается, отправителю уходит ICMP unreachable.
- «Two routes to overlapping networks exist with different prefix lengths and different
  AD. Which is selected?» — маршрут с более длинным префиксом, независимо от AD.
- «A floating static route never becomes active after the primary route fails. What is
  misconfigured?» — административная дистанция floating static ниже, чем у основного
  маршрута, поэтому она уже выбрана как основная (или, наоборот, слишком высока и никогда
  не проходит по AD относительно других резервных источников).
- «`show ip route` shows a valid route to the destination, but ping fails. What should be
  checked next?» — доступность next hop на канальном уровне: ARP, состояние интерфейса,
  соответствие RIB и FIB через `show ip cef`.
