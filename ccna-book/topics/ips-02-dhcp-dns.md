## DHCP: как хост получает адрес

Четыре сообщения, порядок спрашивают постоянно — **DORA**:

| Шаг | Кто | Тип | Адресация |
|---|---|---|---|
| **D**iscover | клиент | broadcast | src 0.0.0.0 → dst 255.255.255.255 |
| **O**ffer | сервер | unicast или broadcast | предлагает адрес |
| **R**equest | клиент | **broadcast** | подтверждает выбранное предложение |
| **A**ck | сервер | unicast | аренда закреплена |

Request идёт широковещательно намеренно: если предложений было несколько, остальные
серверы должны узнать, что их адреса не приняты.

Порты: клиент **UDP 68**, сервер **UDP 67**.

Клиент пытается продлить аренду по достижении **50 %** её срока (T1) и повторяет на
**87,5 %** (T2). Не получил ответа до конца аренды — начинает всё заново и, если ответа
нет вовсе, берёт **APIPA 169.254.x.x**.

## Роутер как DHCP-сервер

```cfg
ip dhcp excluded-address 192.168.10.1 192.168.10.20
!
ip dhcp pool LAN10
 network 192.168.10.0 255.255.255.0
 default-router 192.168.10.1
 dns-server 192.168.10.5 8.8.8.8
 domain-name example.com
 lease 3 0 0                       ! 3 дня
```

`excluded-address` **обязательно** для адресов шлюза, серверов и принтеров — иначе сервер
выдаст их клиентам и получится конфликт. Забытое исключение — типовая причина «дубликат
адреса в сети».

```cli
R1# show ip dhcp binding
IP address       Client-ID/Hardware address   Lease expiration        Type
192.168.10.21    0100.5079.6668.00            Aug 20 2026 09:12 AM    Automatic

R1# show ip dhcp pool
R1# show ip dhcp conflict           ! адреса, где обнаружен конфликт
```

## Relay: сервер в другой подсети

DHCP-запросы широковещательные, а роутер broadcast не пересылает. Чтобы клиенты из VLAN 10
получали адреса от сервера в ЦОД, на интерфейсе-шлюзе этой VLAN включают relay:

```cfg
interface Vlan10
 ip address 192.168.10.1 255.255.255.0
 ip helper-address 10.0.0.50
```

Роутер превращает broadcast в unicast к серверу и **подставляет свой адрес интерфейса
(giaddr)** — по нему сервер понимает, из какой подсети пришёл запрос и из какого пула
выдавать адрес.

> [!key] Запомнить
> `ip helper-address` вешается на интерфейс, **смотрящий в сторону клиентов**, а адрес в
> нём — сервера. Помещать его на интерфейс к серверу — классическая ошибка в вопросах.

Кроме DHCP команда пересылает и другие широковещательные UDP-сервисы (TFTP, DNS, NTP,
TACACS) — это её побочный эффект, о котором иногда спрашивают.

## Клиент на роутере

```cfg
interface GigabitEthernet0/0
 ip address dhcp
```

Так настраивают внешний интерфейс SOHO-роутера, получающего адрес от провайдера.

## Что ломается в DHCP

| Симптом | Причина |
|---|---|
| У всех клиентов 169.254.x.x | сервер недоступен: упал, нет relay, порт не в той VLAN |
| Адрес выдан, но интернета нет | не задан `default-router` в пуле |
| Конфликты адресов | не исключены статические адреса из пула |
| Часть клиентов без адресов | пул исчерпан или слишком мал |
| Работает у сервера в той же VLAN, у других нет | не настроен `ip helper-address` |

## DNS

DNS переводит имя в адрес. Без него связность есть, а «интернет не работает» с точки
зрения пользователя.

- Порт **53**: UDP для обычных запросов, TCP для зонных передач и больших ответов.
- Типы записей, встречающиеся в вопросах: **A** (имя → IPv4), **AAAA** (имя → IPv6),
  **CNAME** (псевдоним), **MX** (почта), **PTR** (обратная зона).
- Разрешение идёт по иерархии: кэш клиента → указанный DNS-сервер → рекурсивный обход от
  корневых серверов.

```cfg
ip name-server 8.8.8.8
ip domain-lookup
ip host SW1 10.0.99.10          ! статическая запись на самом роутере
```

Диагностика: `ping 8.8.8.8` проходит, `ping google.com` — нет → проблема исключительно в
DNS. `nslookup` показывает, какой сервер отвечает и что именно он вернул.

## Разбор DORA с реальными адресами и relay

Клиент в VLAN 10, DHCP-сервер в ЦОД (`10.0.0.50`), на SVI VLAN 10 настроен
`ip helper-address 10.0.0.50`.

```txt
1. Клиент: DHCPDISCOVER, src 0.0.0.0:68 → dst 255.255.255.255:67 (широковещательно, дальше своего сегмента не идёт)
2. Роутер (SVI Vlan10) получает broadcast, видит ip helper-address, пересобирает пакет:
   src 192.168.10.1:67 (giaddr = адрес самого SVI) → dst 10.0.0.50:67, юникастом через сеть
3. Сервер видит giaddr = 192.168.10.1, по нему понимает: "запрос из подсети 192.168.10.0/24",
   выбирает пул именно для неё, отвечает DHCPOFFER юникастом обратно роутеру на 192.168.10.1
4. Роутер разворачивает Offer обратно в сторону VLAN 10 клиенту (снова как broadcast/unicast
   в зависимости от флага broadcast в запросе клиента)
5. Клиент: DHCPREQUEST, снова broadcast — подтверждает выбранное предложение
6. Роутер снова релеит REQUEST на 10.0.0.50, тем же способом, что и Discover
7. Сервер: DHCPACK — аренда закреплена, тем же путём обратно
```

Ключевая деталь для понимания relay: **giaddr — это то единственное, из-за чего сервер
вообще может выдать правильный адрес** клиенту в удалённой подсети. Без relay сервер в
принципе не увидел бы broadcast из VLAN 10 (роутер широковещательный трафик не
пересылает — см. главу про инкапсуляцию), а без giaddr, даже если бы каким-то образом
увидел, не понял бы, из какого пула выдавать.

## Диагностика: relay настроен, но клиенты всё ещё получают APIPA

**Симптом.** `ip helper-address` прописан на SVI, DHCP-сервер в ЦОД жив и обслуживает
другие VLAN нормально, а конкретно эта VLAN продолжает сидеть на `169.254.x.x`.

**Что смотрим.** Есть ли на сервере вообще область (scope) для этой подсети:

```cli
ЦОД-DHCP# show subnet 192.168.10.0
Error: subnet not found
```

**Что нашли.** Сервер прекрасно получает релееные запросы (сетевая связность в порядке —
других VLAN это не касается, значит проблема не в маршруте до сервера), но у него **нет
настроенной области** под `192.168.10.0/24` — он получает DHCPDISCOVER с giaddr
192.168.10.1, честно смотрит, из какого пула выдавать, не находит подходящего и
**молчит**, не отвечая вовсе. С точки зрения клиента это неотличимо от «сервер
недоступен» — оба случая заканчиваются одинаковым APIPA после серии таймаутов. Разница
видна только на самом сервере: относится ли симптом к сетевой связности (`ip
helper-address`, ACL, маршрут) или к отсутствующей конфигурации области — сервер либо
недостижим вовсе, либо достижим, но не настроен на эту подсеть.

> [!trap] Ловушка
> «APIPA — значит, сервер недоступен» — не единственное объяснение. Сервер может быть
> полностью доступен и релей настроен правильно, а причина — просто отсутствующая область
> для конкретной подсети на самом сервере.

## Диагностика: конфликт адресов у принтера после переезда офиса

**Симптом.** У сетевого принтера со статически заданным адресом `192.168.10.5` время от
времени пропадает связь, в логе роутера — запись о конфликте.

**Что смотрим.** Список исключённых адресов пула:

```cli
R1# show running-config | section ip dhcp pool LAN10
ip dhcp pool LAN10
 network 192.168.10.0 255.255.255.0
 default-router 192.168.10.1
 dns-server 192.168.10.5 8.8.8.8
```

**Что нашли.** В конфигурации нет ни одной строки `ip dhcp excluded-address` — весь
диапазон `192.168.10.0/24`, включая `.5`, доступен серверу для динамической выдачи. Рано
или поздно DHCP выдаст этот же адрес другому клиенту, и оба устройства окажутся с
одинаковым IP — принтер видит обрывы именно тогда, когда конфликтующий клиент активен в
сети. Обрати внимание: адрес DNS-сервера в пуле (`192.168.10.5`) совпадает со статическим
адресом принтера в этом примере не случайно — типичная причина подобных конфликтов в
том, что при первоначальной настройке пула просто забыли учесть уже занятые вручную
адреса. Лечится одной строкой, добавленной **до** активной раздачи новых адресов:

```cfg
ip dhcp excluded-address 192.168.10.1 192.168.10.10
```

## Разбор: путь DNS-запроса от кэша до корневых серверов

`nslookup shop.example.com`, у клиента пусто в локальном кэше:

```txt
1. Клиент → свой настроенный DNS-сервер (резолвер, например 8.8.8.8): "shop.example.com?"
2. Резолвер не знает ответа, тоже не в кэше → идёт к корневому серверу (.)
3. Корневой сервер не хранит записи сайтов, но знает, кто отвечает за .com → отсылает к TLD-серверу .com
4. TLD-сервер .com не знает shop.example.com, но знает NS-серверы example.com → отсылает к ним
5. Сервер example.com авторитативен именно для этого домена → отдаёт A-запись shop.example.com
6. Резолвер кэширует ответ на время TTL записи и возвращает его клиенту
```

Экзаменационная деталь: шаги 2–5 — это **рекурсивный** поиск, который выполняет резолвер
клиента, а не сам клиент; клиент делает только шаг 1 и получает готовый ответ. Повторный
запрос того же имени от другого клиента к тому же резолверу отработает мгновенно из кэша
(шаг 6), пока не истечёт TTL записи — отсюда объясняется задержка после смены DNS-записи
на сервере: изменения не видны никому, у кого адрес ещё жив в чужом кэше.

## Что спрашивают

- «What is the order of DHCP messages?» — Discover, Offer, Request, Ack.
- «Which message is broadcast by the client?» — Discover и Request.
- «Where is ip helper-address configured?» — на интерфейсе со стороны клиентов, с адресом
  сервера.
- «A host received 169.254.x.x. What is the cause?» — DHCP недоступен.
- «Which command excludes addresses from being assigned?» — `ip dhcp excluded-address`.
- «Ping by IP works, by name fails» — DNS.
- «Which port does DNS use?» — 53 (UDP, и TCP для зон).
- «What field does a DHCP relay agent insert so the server knows which subnet's pool to
  use?» — giaddr, адрес интерфейса-релея, обращённого к клиенту.
- «`ip helper-address` is correctly configured and the DHCP server is reachable, but
  clients still receive an APIPA address. What else should be checked?» — настроена ли
  на сервере область (scope) именно для этой подсети — сервер может быть доступен, но
  просто не иметь под неё конфигурации.
- «A statically addressed printer intermittently loses connectivity and the router logs
  an address conflict. What is missing from the DHCP pool?» — `ip dhcp excluded-address`
  для диапазона, включающего статический адрес принтера.
- «Who performs the recursive part of DNS resolution — the client or its configured
  resolver?» — резолвер (DNS-сервер, указанный у клиента); сам клиент делает только один
  запрос и получает готовый ответ.
