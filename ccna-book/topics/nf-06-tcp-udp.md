## Один вопрос: нужна ли гарантия

Оба протокола работают на четвёртом уровне и оба несут **порты**, чтобы разделить
приложения на одном узле. Дальше начинается расхождение.

| | TCP | UDP |
|---|---|---|
| Соединение | устанавливается (three-way handshake) | нет, шлём сразу |
| Подтверждения | каждый сегмент подтверждается | нет |
| Порядок | восстанавливается по sequence number | не гарантирован |
| Потери | повторная передача | приложение решает само |
| Управление потоком | скользящее окно | нет |
| Заголовок | 20 байт и больше | 8 байт |
| Накладные расходы | заметные | минимальные |
| Кому подходит | файлы, почта, веб, БД | голос, видео, DNS, DHCP, SNMP, TFTP |

> [!key] Запомнить
> UDP выбирают не потому, что «не важна доставка», а потому, что **повтор бесполезен**:
> голосовой пакет, пришедший на 300 мс позже, уже никому не нужен, а его повторная
> передача только добавит задержки.

## Тройное рукопожатие и разрыв

```txt
   Клиент                        Сервер
      |  SYN  seq=x                  |
      |----------------------------->|
      |  SYN-ACK  seq=y, ack=x+1     |
      |<-----------------------------|
      |  ACK  ack=y+1                |
      |----------------------------->|
      |        данные пошли          |
```

Разрыв — четыре шага (FIN, ACK, FIN, ACK) либо резкий сброс одним **RST**.

Это спрашивают в форме «какой флаг увидим первым», «сколько сообщений нужно для
установки» и «что означает RST в дампе» (соединение отвергнуто или сброшено, порт закрыт).

## Что делают поля заголовка TCP

- **Sequence number** — номер первого байта в сегменте: получатель по нему складывает
  поток в правильном порядке.
- **Acknowledgment number** — номер следующего ожидаемого байта, то есть «всё до него
  получено».
- **Window size** — сколько байт отправитель может послать без подтверждения. Это и есть
  **управление потоком**: получатель уменьшает окно, когда не успевает разбирать буфер,
  и увеличивает, когда справляется. Окно нулевого размера — «подожди, я захлебнулся».
- **Флаги** — SYN, ACK, FIN, RST, PSH, URG.

UDP-заголовок содержит всего четыре поля: порт источника, порт назначения, длина,
контрольная сумма. Ни номеров, ни окна — потому и 8 байт.

## Разбор задачи: чтение списка активных сессий

Инженеру дают вывод и спрашивают, что здесь происходит:

```txt
Proto  Local Address          Foreign Address        State
TCP    192.168.1.10:51223     93.184.216.34:443       ESTABLISHED
TCP    192.168.1.10:51224     93.184.216.34:443       ESTABLISHED
TCP    192.168.1.10:22        0.0.0.0:0                LISTENING
UDP    192.168.1.10:68        *:*                      -
UDP    192.168.1.10:5353      *:*                      -
```

Что тут читают по порядку:

1. **Первые две строки** — два отдельных TCP-соединения к одному и тому же серверу на 443
   (HTTPS), различаются только source-портом. Это две вкладки браузера к одному сайту, а не
   ошибка или дубликат.
2. **Третья строка** — локальная служба SSH **слушает** входящие соединения (`LISTENING`),
   но сама сессия ещё не установлена — foreign address `0.0.0.0:0` означает «кто угодно
   ещё не подключился».
3. **UDP-строки** — у UDP нет состояния `ESTABLISHED`/`LISTENING` в принципе, поэтому в
   графе State обычно прочерк или условное «активен»: 68 — DHCP-клиент, 5353 — mDNS
   (обнаружение устройств в локальном сегменте).

Вывод, который отсюда экзаменуют: колонка **State** информативна только для TCP; для UDP
её отсутствие — не признак проблемы, а свойство протокола.

> [!trap] Ловушка
> DNS работает **и по UDP, и по TCP**: обычный запрос — UDP/53, перенос зоны и ответ, не
> влезающий в лимит, — TCP/53. Вариант «только UDP» в вопросе про DNS не всегда верен —
> читай, о чём именно спрашивают.

## Сокет и как различаются сессии

Сессию однозначно определяет пятёрка: **протокол + IP источника + порт источника + IP
назначения + порт назначения**. Поэтому два окна браузера к одному сайту не путаются: у
них разные динамические порты источника.

```cli
R1# show ip nat translations
Pro Inside global      Inside local       Outside local      Outside global
tcp 203.0.113.5:1055   192.168.1.10:1055  93.184.216.34:80   93.184.216.34:80
tcp 203.0.113.5:1056   192.168.1.11:1056  93.184.216.34:80   93.184.216.34:80
```

## Почему приложение выбрало именно этот протокол

- **Голос и видео (RTP)** — UDP: важна равномерная задержка, потерянный пакет проще
  заглушить, чем ждать повтор.
- **DHCP** — UDP: клиент ещё не имеет адреса, соединение устанавливать не с чем и не с
  чего; сообщения широковещательные.
- **TFTP** — UDP: протокол намеренно простой, всю надёжность реализует сам, за счёт этого
  влезает в загрузчик устройства.
- **Веб, почта, передача файлов** — TCP: потерянный байт делает файл непригодным.
- **SNMP** — UDP: опрос сотен устройств не должен стоить соединения на каждое.

## Разбор передачи данных по шагам: seq и ack в движении

Рукопожатие выше показывает старт, но вопросы часто просят проследить номера **дальше**,
уже во время передачи данных. Клиент после установления соединения (SYN=x, SYN-ACK=y)
шлёт запрос из 500 байт.

```txt
Клиент (ISN=x)                              Сервер (ISN=y)
   seq=x+1  ack=y+1  len=500  "GET /page..."
   ----------------------------------------->
                                    seq=y+1  ack=x+501  (подтверждение + начало ответа)
   <-----------------------------------------
   seq=x+501  ack=y+2001  len=0   (просто ACK, данных нет)
   ----------------------------------------->
```

Правило, которое тут проверяют: **acknowledgment number = seq байта, который отправитель
ждёт следующим**, то есть seq полученного сегмента плюс его длина в байтах (SYN и FIN
считаются как один байт каждый, поэтому после SYN=x идёт seq=x+1). Сервер, приславший 2000
байт ответа начиная с seq=y+1, получит от клиента `ack=y+2001` — не «ack на каждый пакет
отдельно», а один ack, покрывающий весь непрерывный блок принятых данных сразу
(это и называется **накопительное подтверждение**, cumulative ACK).

## Диагностика: браузер «висит», а в дампе только SYN без ответа

**Симптом.** Пользователь открывает сайт, вкладка крутится и через минуту показывает
таймаут. `ping` до сервера при этом проходит.

**Что смотрим.** Захват трафика с клиента:

```txt
12:00:01.001  Client → Server  [SYN]  seq=0
12:00:04.001  Client → Server  [SYN]  seq=0   (retransmission)
12:00:10.001  Client → Server  [SYN]  seq=0   (retransmission)
12:00:22.001  Client → Server  [SYN]  seq=0   (retransmission)
```

**Что нашли.** Клиент честно повторяет SYN с экспоненциально растущей паузой (это
поведение TCP-стека при потере пакета или отсутствии ответа) — и ни разу не получает ни
SYN-ACK, ни RST. Раз `ping` (ICMP, L3) до узла доходит, а TCP-сегмент до порта — нет,
причина не в маршруте, а именно в этом порту: где-то на пути ACL или stateful firewall
**молча отбрасывает** SYN на нужный TCP-порт, не отвечая ничем. Это отличается от
следующего случая.

## Диагностика: «connection refused» против «connection timed out»

Два разных сообщения об одной и той же недоступности порта — и они означают разное:

| Сообщение | Что произошло на проводе | Где искать |
|---|---|---|
| **Connection refused** | пришёл `RST` в ответ на `SYN` | узел доступен, порт закрыт — служба не запущена или не слушает этот порт |
| **Connection timed out** | ответа нет вовсе, клиент только ретрансмиттит `SYN` | пакет отброшен молча — ACL/firewall по пути, либо узел недоступен физически |

```cli
PC> telnet 10.3.3.30 3389
Trying 10.3.3.30...
% Connection refused by remote host
```

`refused` в этом выводе — прямое доказательство, что до узла TCP дошёл, а вот `Trying...`
без ответа, зависшее надолго, — сигнал смотреть фильтрацию по пути, а не на сам сервер.

> [!key] Запомнить
> RST — это ответ живого стека, которому нечего слушать на этом порту. Тишина — это либо
> узел недоступен на L3 (тогда и ping не пройдёт), либо кто-то фильтрует именно этот трафик,
> не уведомляя отправителя.

## Диагностика: голос рвётся, а веб на том же канале работает нормально

**Симптом.** В параллельном разговоре по IP-телефонии слышны щелчки и обрывы слов, при
этом обычный веб-сёрфинг и файлы по тому же каналу не жалуются.

**Что смотрим.** Считаем потери и джиттер, а не пропускную способность:

```cli
R1# show interfaces gi0/1 | include drops|output errors
  Output queue: 0/40 (size/max)
  Total output drops: 128
```

**Что нашли.** На интерфейсе есть **output drops** — очередь периодически переполняется на
короткое время под пиковой нагрузкой. TCP-трафик веб-сёрфинга эту потерю просто не заметит
на глаз: отправитель снизит окно, повторно пошлёт потерянный сегмент, страница откроется на
доли секунды позже. У голоса, который идёт по **RTP поверх UDP**, повторной передачи нет —
потерянный пакет исчезает навсегда, и джиттер-буфер приёмника либо сглаживает это (тишина
доли секунды), либо нет (щелчок, обрыв слова). Отсюда практический вывод, который
спрашивают именно как факт: **TCP прячет потери ценой задержки, UDP показывает потери
пользователю сразу** — и для голоса это меньшее зло, чем задержка от повторной передачи.
Лечится это уже не на уровне модели транспорта, а через QoS-очереди с приоритетом для
голосового трафика — тема отдельной главы.

## Управление потоком: разбор задачи на окно

Клиенту с window size 4000 байт и RTT (время туда-обратно) 100 мс сервер может передавать
непрерывно, только если получает подтверждения быстрее, чем заканчивается окно.

```txt
   Пропускная способность ≈ окно / RTT = 4000 байт / 0,1 с = 40 000 байт/с ≈ 320 кбит/с
```

Даже если сам канал способен на гигабит, скорость передачи **этой конкретной сессии**
упрётся в 320 кбит/с, пока получатель не увеличит окно (что он и делает динамически, если
успевает разбирать буфер). Отсюда экзаменационная логика: маленькое окно на медленном или
перегруженном канале — не поломка, а осознанное **управление потоком**, которое защищает
получателя от переполнения, а не жадность протокола.

## MSS: сколько данных реально влезает в один сегмент

**Maximum Segment Size** — поле, которым стороны обмениваются прямо в SYN и SYN-ACK,
задолго до передачи данных, и оно напрямую связано с MTU из главы про инкапсуляцию:

```txt
Ethernet MTU               1500 байт
− заголовок IP (без опций)   20 байт
− заголовок TCP (без опций)  20 байт
= MSS                       1460 байт
```

Каждая сторона объявляет своё значение MSS (обычно производное от MTU своего исходящего
интерфейса), и **используется меньшее** из двух объявленных — точно так же, как окно
ограничивается более медленной стороной. Если на пути есть туннель (GRE, IPsec), который
добавляет свои байты заголовка, MSS нужно уменьшить вручную на обоих концах — иначе
получится ситуация «маленькие пакеты ходят, большие эффективно ходят с проблемами»,
знакомая по MTU-диагностике из предыдущей главы, только на транспортном уровне.

## Диагностика: файл копируется медленно, в захвате много Retransmission

**Симптом.** Копирование большого файла по TCP занимает в разы дольше ожидаемого, канал по
факту не загружен целиком.

**Что смотрим.** Долю повторных передач в захвате трафика:

```txt
1000 сегментов отправлено
   870 подтверждено с первого раза
   130 отмечены как [TCP Retransmission] или [TCP Dup ACK]
```

**Что нашли.** 13% повторов — это не окно (окно регулирует скорость, а не количество
потерь) и не MSS (тот просто ограничивает размер каждого куска). Такая доля retransmission
почти всегда означает **потерю пакетов на пути** — перегруженный линк, плохой Wi-Fi,
ошибающийся интерфейс (см. счётчики CRC/input errors из главы про модели OSI). TCP
компенсирует потерю повтором, поэтому передача формально не рвётся — но каждый повтор это
цикл ожидания таймаута или **fast retransmit** (три подряд дублирующих ACK заставляют
отправителя повторить сегмент, не дожидаясь полного таймера) плюс, как правило, снижение
окна перегрузки (**congestion window**) после каждой такой потери. Результат — файл
докачивается, но заметно медленнее, чем позволяет чистый канал. Экзаменационный вывод:
медленная, но не рвущаяся TCP-передача указывает на потери по пути, а не на нехватку
пропускной способности как таковой.

> [!trap] Ловушка
> «Скорость передачи низкая — узкий канал» верно не всегда: TCP намеренно снижает скорость
> в ответ на потери (алгоритм congestion control), поэтому реальная причина медленной
> передачи часто в потерях на промежуточном линке, а не в ширине канала на конце.

## Сводка: пять симптомов транспортного уровня и куда смотреть

| Симптом | Что проверить | Вероятная причина |
|---|---|---|
| Тайм-аут, SYN без ответа, ping проходит | ACL/firewall на пути к нужному TCP-порту | молчаливая фильтрация |
| Connection refused сразу | служба на целевом порту | порт закрыт, слушателя нет |
| Медленно, но не рвётся | доля Retransmission в захвате | потери на промежуточном линке |
| Голос рвётся, файлы качаются нормально | output drops на интерфейсах пути | нехватка приоритета для UDP/RTP в очереди |
| DNS не резолвит без явной ошибки | приход ICMP port unreachable | служба недоступна либо ICMP отфильтрован |

Общая логика для всех пяти строк одна: сначала подтверждаем, что проблема не на L3
(`ping`, доступность узла), затем смотрим, что именно сообщает — или не сообщает — сам
транспортный уровень, и только потом переходим к конкретной причине. Тишина в ответ почти
всегда означает фильтрацию где-то по пути, а не поломку на конечном узле.

## Состояния TCP-соединения: что видно в `show tcp brief`

Соединение TCP живёт не только «установлено / не установлено» — у него есть промежуточные
состояния, и они тоже спрашиваются.

```cli
R1# show tcp brief all
TCB       Local Address           Foreign Address        (state)
665F2A18  10.1.1.1.23             10.1.1.10.51223         ESTAB
665F3B20  10.1.1.1.179            10.2.2.2.44012           SYNSENT
665F1C90  10.1.1.1.23             *.*                      LISTEN
```

| Состояние | Что происходит |
|---|---|
| `LISTEN` | служба поднята и ждёт входящий SYN, соединения ещё нет |
| `SYN_SENT` | локальная сторона отправила SYN и ждёт SYN-ACK |
| `SYN_RECEIVED` | пришёл SYN, отправлен SYN-ACK, ждём финальный ACK |
| `ESTABLISHED` | рукопожатие завершено, идёт обмен данными |
| `FIN_WAIT` / `CLOSE_WAIT` | одна из сторон начала закрывать соединение |
| `TIME_WAIT` | соединение закрыто, но сокет ещё держится (обычно 2 минуты) — на случай, если последний ACK потерялся |

Практический смысл: если `show tcp brief` неделями показывает десятки записей в
`SYN_RECEIVED` без перехода в `ESTABLISHED`, это отпечаток **SYN flood** — атакующий шлёт
SYN пачками и не завершает рукопожатие, забивая таблицу полуоткрытых соединений. Одна
запись в `SYN_SENT`, зависшая надолго, — это тот же случай молчаливо отфильтрованного
ответа, который разобран выше. Большое число сессий в `TIME_WAIT` на активно используемом
сервере — обычно не проблема сама по себе, а следствие короткоживущих HTTP-соединений,
которые корректно закрываются одна за другой; тревожным сигналом это становится, только
если сокетов не хватает под новые соединения.

## Диагностика: DNS не резолвит, а ошибки соединения нет

**Симптом.** Приложение просто не получает ответа на DNS-запрос и через некоторое время
сообщает «сервер не найден» — без явного «отказано» или «недоступно».

**Что смотрим.** Тип протокола под DNS: UDP, и у него нет ни SYN, ни RST, ни какого-либо
другого явного сигнала «порт закрыт» на транспортном уровне — только сам факт отсутствия
ответа. Единственная подсказка, которая может прийти по сети, — ICMP:

```txt
ICMP Type 3, Code 3 — Destination Unreachable (Port Unreachable)
```

**Что нашли.** Если ICMP port unreachable дошёл — сервер жив, но служба на UDP/53 не
слушает (не запущена, не тот порт). Если не дошло вообще ничего — либо узел недоступен на
L3, либо сообщение фильтруется по пути так же, как ICMP Fragmentation Needed в примере
из главы про инкапсуляцию. Ключевой вывод для экзамена: **у UDP нет своего аналога RST** —
телом протокола эта информация никогда не передаётся, только опционально через ICMP или
через логику самого приложения (DNS resolver просто уйдёт в таймаут и попробует следующий
сервер из списка).

> [!trap] Ловушка
> «Соединение отклонено» звучит как термин TCP не просто так — у UDP не бывает «refused» в
> строгом смысле рукопожатия, потому что рукопожатия нет. Формулировка вопроса
> «connection refused for a UDP-based service» почти всегда описывает именно ICMP port
> unreachable, а не флаг протокола.

## Что спрашивают

- «Which two characteristics describe UDP?» — без установления соединения, без
  подтверждений, минимальные накладные расходы, подходит для голоса.
- «What is the purpose of the window size field?» — управление потоком.
- «Refer to the exhibit… which protocol is used?» — по номеру порта в выводе.
- «Which protocol is used by a client to obtain an IP address automatically?» — DHCP
  поверх UDP 67/68.
- «Why is UDP preferred for voice?» — низкая задержка, повтор бесполезен.
- Сопоставления «порт → протокол» в drag-and-drop.
- «A host receives a TCP RST in response to a connection attempt. What does this
  indicate?» — узел доступен, но порт закрыт или служба не слушает — это не проблема сети.
- «A client repeatedly retransmits SYN segments and never receives a response. Ping to the
  same host succeeds. What is the most likely cause?» — ACL или firewall на пути молча
  отбрасывает трафик именно на этот TCP-порт.
- «Which acknowledgment number will host B send after receiving a 500-byte segment with
  sequence number 1000?» — 1500: ack = sequence + длина принятых данных.
- «Why does TCP handle packet loss differently from UDP in terms of user experience?» —
  TCP скрывает потерю за счёт повторной передачи и задержки; UDP отдаёт потерю
  приложению немедленно, без повтора.
- «What is a disadvantage of a very small TCP window size on a high-bandwidth link?» —
  пропускная способность сессии ограничена окном, делённым на RTT, и может быть далеко
  ниже возможностей самого канала.
- «What is the purpose of the Maximum Segment Size (MSS)?» — задать наибольший размер
  данных в одном TCP-сегменте, чтобы итоговый пакет не превысил MTU пути.
- «A file transfer completes but takes much longer than expected. A capture shows a high
  percentage of retransmissions. What is the likely cause?» — потери пакетов на пути
  (перегрузка, ошибающийся линк), а не нехватка полосы канала как таковая.
- «What condition is indicated by many connections stuck in the SYN_RECEIVED state?» —
  вероятный SYN flood: полуоткрытые соединения не завершаются намеренно.
- «Which field changes when a packet passes through a device that adds encapsulation, such
  as a GRE or IPsec tunnel?» — эффективный MTU пути уменьшается, и MSS на обоих концах
  нужно скорректировать вручную, иначе крупные сегменты будут теряться или фрагментироваться.

## Проверь себя

```check
?? Сколько сообщений нужно, чтобы установить TCP-соединение, и как они называются?
!! Три: SYN, SYN-ACK, ACK.
?? Получатель прислал window size = 0. Что это значит и что сделает отправитель?
!! Буфер получателя переполнен; отправитель приостановит передачу до обновления окна.
?? Приложение шлёт короткие запросы сотням устройств и переживёт потерю ответа. Какой транспорт логичен?
!! UDP — так работает, например, SNMP.
?? На каких портах живут SSH, Telnet и HTTPS?
!! 22, 23 и 443 соответственно, все по TCP.
?? Чем отличаются acknowledgment number и sequence number?
!! Sequence — номер первого байта в этом сегменте; acknowledgment — номер следующего ожидаемого байта, подтверждающий всё до него.
?? Telnet до порта возвращает Connection refused. Что это значит для сети?
!! Сеть в порядке: TCP-сегмент дошёл до узла, но на порту нет слушающей службы или она явно отвергла подключение — пришёл RST.
?? Клиент раз за разом ретрансмиттит SYN и не получает ни SYN-ACK, ни RST, хотя ping до узла проходит. Где искать проблему?
!! Не на самом узле (он отвечает на ICMP), а по пути — ACL или stateful firewall молча отбрасывает трафик на этот TCP-порт.
?? Почему обрывы голоса в разговоре не лечатся тем же способом, что и потери при скачивании файла?
!! Файл идёт по TCP и потерянный сегмент просто перезапросится ценой небольшой задержки; голос идёт по RTP поверх UDP без повтора — потерянный пакет пропадает навсегда, и лечить нужно QoS-приоритетом в очереди, а не повторной передачей.
?? Окно получателя 4000 байт, RTT канала 100 мс. Какая максимальная скорость этой сессии, даже если канал гигабитный?
!! Около 320 кбит/с (4000 байт / 0,1 с) — сессию ограничивает окно, а не физическая скорость канала, пока окно не увеличится.
?? Из чего складывается MSS 1460 байт при обычном Ethernet MTU 1500?
!! 1500 минус 20 байт заголовка IP минус 20 байт заголовка TCP (без опций) = 1460.
?? DNS-запрос по UDP не получил ответа. Какой сигнал по сети мог бы сообщить, что порт закрыт, и получает ли его обычно приложение?
!! ICMP Destination Unreachable, код Port Unreachable — но он опционален и часто фильтруется, поэтому приложение обычно узнаёт о проблеме только по собственному таймауту.
?? Захват показывает сотни соединений в состоянии SYN_RECEIVED, которые не переходят в ESTABLISHED. О чём это говорит?
!! Похоже на SYN flood: атакующий шлёт SYN пачками и намеренно не завершает рукопожатие, забивая таблицу полуоткрытых соединений сервера.
```
