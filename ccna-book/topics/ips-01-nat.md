## Зачем NAT

Публичных IPv4-адресов не хватает, а внутри сети живут приватные адреса (RFC 1918),
которые в интернете не маршрутизируются. **NAT подменяет адрес в заголовке пакета**, когда
он пересекает границу сети, и восстанавливает обратно для ответа.

Побочный, но регулярно спрашиваемый эффект: внутренняя адресация **скрыта** от внешнего
мира, и снаружи нельзя инициировать соединение к хосту, для которого нет явной трансляции.

## Четыре имени одного адреса

| Термин | Чей адрес | Как выглядит |
|---|---|---|
| **Inside local** | внутренний хост, как его видят внутри | 192.168.1.10 |
| **Inside global** | тот же хост, как его видят снаружи | 203.0.113.5 |
| **Outside global** | внешний сервер, как его видят снаружи | 93.184.216.34 |
| **Outside local** | внешний сервер, как его видят изнутри | обычно тот же 93.184.216.34 |

Мнемоника: **local — «как называется внутри», global — «как называется снаружи»; inside —
чей адрес наш, outside — чужой.** Эти четыре слова спрашивают почти в каждом наборе
вопросов по NAT.

## Три вида

### Статический NAT — один к одному

```cfg
ip nat inside source static 192.168.1.10 203.0.113.10
!
interface GigabitEthernet0/1
 ip nat inside
interface GigabitEthernet0/0
 ip nat outside
```

Нужен для серверов, к которым обращаются снаружи: адрес фиксирован и постоянен.
Разновидность с портами (**port forwarding**):

```cfg
ip nat inside source static tcp 192.168.1.10 80 203.0.113.5 8080
```

### Динамический NAT — из пула

```cfg
ip nat pool OFFICE 203.0.113.10 203.0.113.20 netmask 255.255.255.0
access-list 1 permit 192.168.1.0 0.0.0.255
ip nat inside source list 1 pool OFFICE
```

Каждому внутреннему хосту достаётся свободный адрес из пула на время сессии. **Адреса
кончились — новые хосты наружу не выйдут** (пакеты отбрасываются, отправителю уходит ICMP
unreachable). Это стандартный вопрос про исчерпание пула.

### PAT (NAT overload) — много к одному

```cfg
access-list 1 permit 192.168.1.0 0.0.0.255
ip nat inside source list 1 interface GigabitEthernet0/0 overload
```

Все внутренние хосты выходят под **одним** адресом, а различают их **номера портов
источника**. Именно так работает любой домашний роутер. Одного публичного адреса хватает
на тысячи одновременных сессий.

> [!key] Запомнить
> Ключевое слово **`overload`** превращает NAT в PAT. Без него та же строка с пулом даст
> обычный динамический NAT «один к одному».

## Обязательные шаги

Какой бы вариант ни выбрали, нужны три вещи, и забывают обычно третью:

1. Правило трансляции (`ip nat inside source …`).
2. `ip nat inside` на внутреннем интерфейсе.
3. `ip nat outside` на внешнем.

Без пометки интерфейсов роутер просто не поймёт, где граница, и трансляции не будет.

## Чтение таблицы

```cli
R1# show ip nat translations
Pro Inside global      Inside local       Outside local      Outside global
--- 203.0.113.10       192.168.1.10       ---                ---
tcp 203.0.113.5:1055   192.168.1.20:1055  93.184.216.34:80   93.184.216.34:80
tcp 203.0.113.5:1056   192.168.1.21:3344  93.184.216.34:80   93.184.216.34:80

R1# show ip nat statistics
Total active translations: 3 (1 static, 2 dynamic; 2 extended)
Outside interfaces: GigabitEthernet0/0
Inside interfaces: GigabitEthernet0/1
Hits: 12043  Misses: 12
```

Строка без протокола — статическая трансляция; строки с `tcp` и портами — PAT (extended).
Одинаковый inside global у двух записей с разными портами и есть перегрузка.

Очистка: `clear ip nat translation *`.

## Что ломается

| Симптом | Причина |
|---|---|
| Трансляций нет вообще | не помечены интерфейсы `ip nat inside/outside` |
| Часть хостов не выходит | ACL в правиле не покрывает их подсеть |
| «Кончились адреса» | исчерпан пул динамического NAT — нужен `overload` |
| Снаружи не достучаться до сервера | нет статической трансляции/port forwarding |
| Работает, но ломается FTP/SIP | протоколы, передающие адрес внутри данных, требуют ALG |

## NAT и IPv6

В IPv6 адресов достаточно, и NAT в привычном виде не нужен — вместо него используют
**NAT64** для доступа IPv6-клиента к IPv4-ресурсу. Формулировку «IPv6 требует NAT для
выхода в интернет» в вариантах ответа отмечай как неверную.

## Разбор: сквозной путь пакета через PAT

PC (`192.168.1.20`) открывает страницу на сервере `93.184.216.34:80` через роутер с
`overload` на внешнем интерфейсе `203.0.113.5`.

```txt
1. PC отправляет пакет: src 192.168.1.20:51223 → dst 93.184.216.34:80
2. Роутер видит исходящий пакет на inside-интерфейсе, ищет совпадение в ACL правила NAT,
   транслирует source: 192.168.1.20:51223 → 203.0.113.5:1055
   (порт при этом обычно меняется — оригинальный 51223 мог уже использоваться другим
   хостом; таблица запоминает пару "было / стало")
3. Пакет уходит наружу: src 203.0.113.5:1055 → dst 93.184.216.34:80
4. Сервер отвечает на адрес, который видел: src 93.184.216.34:80 → dst 203.0.113.5:1055
5. Роутер получает ответ на outside-интерфейсе, ищет 203.0.113.5:1055 в таблице трансляций,
   переписывает destination обратно: 93.184.216.34:80 → dst 192.168.1.20:51223
6. Пакет доходит до PC с исходным адресом сервера, как будто NAT не было вовсе
```

Ключевая деталь, которую спрашивают отдельно: **PC не знает о существовании NAT** — с его
точки зрения сессия идёт напрямую до `93.184.216.34`, вся подмена происходит на роутере в
обе стороны симметрично. Именно поэтому запись в таблице трансляций создаётся **исходящим**
пакетом и используется для обратного перевода **входящего** — без исходящего пакета от PC
входящий с той же парой портов роутер бы просто отбросил как неизвестный (это и есть
причина, по которой снаружи нельзя самостоятельно достучаться до внутреннего хоста без
статической трансляции).

## Диагностика: часть офиса не выходит в интернет, часть работает

**Симптом.** PAT настроен и работает для большинства сотрудников, но пользователи из
одной конкретной подсети жалуются на полное отсутствие доступа в интернет.

**Что смотрим.** Покрывает ли ACL, на который ссылается правило NAT, все внутренние сети:

```cli
R1# show access-lists 1
Standard IP access list 1
    10 permit 192.168.1.0, wildcard bits 0.0.0.255 (14021 matches)

R1# show ip route | include connected
C    192.168.1.0/24 is directly connected, GigabitEthernet0/1
C    192.168.2.0/24 is directly connected, GigabitEthernet0/2
```

**Что нашли.** ACL 1 разрешает только `192.168.1.0/24` — вторая внутренняя подсеть,
`192.168.2.0/24`, физически подключена к роутеру и маршрутизируется нормально, но **не
входит** в список, который NAT считает подлежащим трансляции. Пакеты от неё доходят до
роутера, но уходят наружу с приватным source-адресом — и либо отбрасываются провайдером
(приватные адреса не маршрутизируются в интернете, см. главу про IPv4-адресацию), либо
теряются на первом устройстве, которое проверяет источник. Лечится добавлением сети в тот
же (или отдельный) ACL:

```cfg
access-list 1 permit 192.168.2.0 0.0.0.255
```

> [!trap] Ловушка
> «NAT настроен, но не работает у части сети» почти никогда не означает поломку самого
> NAT — сначала проверяют, входит ли конкретная подсеть в ACL правила трансляции. Список
> `show ip route` подскажет, какие сети вообще существуют и должны быть покрыты.

## Диагностика: пул динамического NAT исчерпан

**Симптом.** Утром пользователи выходят в интернет нормально, к обеду новые подключения
перестают работать, хотя уже открытые сессии продолжают жить.

**Что смотрим.** Статистику использования пула:

```cli
R1# show ip nat statistics
Total active translations: 11 (0 static, 11 dynamic; 0 extended)
Pool OFFICE: netmask 255.255.255.0
        start 203.0.113.10 end 203.0.113.20
        type generic, total addresses 11, allocated 11 (100%), misses 340
```

**Что нашли.** `allocated 11 (100%)` — пул из 11 адресов занят полностью, и `misses 340`
показывает, сколько раз новым сессиям **не хватило** свободного адреса. Это динамический
NAT без `overload` — каждому хосту нужен отдельный адрес на время сессии, а не порт, и
как только пул исчерпан, новые хосты не транслируются вовсе, пока какая-то из текущих
сессий не завершится и не освободит адрес. Экзаменационный вывод: правильное решение —
не «расширить пул до бесконечности», а **добавить `overload`**, превратив NAT в PAT — тогда
одного-двух адресов хватит на весь офис, потому что различение идёт по портам, а не по
целым адресам.

## Диагностика: сервер внутри сети недоступен снаружи

**Симптом.** Веб-сервер `192.168.1.50:443` работает внутри сети нормально, но
пользователи из интернета не могут открыть сайт по публичному адресу компании.

**Что смотрим.** Есть ли для этого хоста именно **статическая** трансляция, а не только
общее правило PAT для исходящего трафика:

```cli
R1# show ip nat translations | include 192.168.1.50
```

**Что нашли.** Пусто — в таблице нет записи для этого адреса вовсе, и это ожидаемо: общее
правило `ip nat inside source list 1 interface Gi0/0 overload` транслирует только
**исходящие** соединения, инициированные изнутри. Оно не создаёт постоянного соответствия,
на которое мог бы прийти **входящий** запрос снаружи — PAT в принципе не умеет
«угадывать», какому внутреннему хосту адресован незапрошенный входящий пакет. Для
публикации сервера нужна отдельная статическая (в данном случае — с портом, раз важен
конкретный сервис) трансляция:

```cfg
ip nat inside source static tcp 192.168.1.50 443 203.0.113.5 443
```

## Что спрашивают

- «Which term describes the address of an inside host as seen from the internet?» —
  inside global.
- «Which command enables PAT?» — правило с `overload`.
- «Refer to the exhibit… what does this NAT table show?» — статические против
  динамических, наличие портов.
- «What happens when the NAT pool is exhausted?» — новые хосты не получают трансляцию.
- «Which two interfaces must be defined?» — `ip nat inside` и `ip nat outside`.
- Drag-and-drop: разложить четыре термина NAT по адресам из схемы.
- «PAT is configured and works for most hosts, but one subnet has no internet access at
  all. What should be checked?» — покрывает ли ACL правила NAT эту конкретную подсеть.
- «`show ip nat statistics` shows a pool allocated at 100% with growing misses. What is
  the correct fix?» — добавить `overload` (превратить в PAT), а не бесконечно расширять
  пул адресов.
- «An internal web server is reachable from inside the network but not from the
  internet, even though PAT overload is configured for outbound traffic. What is
  missing?» — отдельная статическая трансляция (со статическим портом) для этого сервера
  — общий PAT транслирует только исходящие соединения.
- «Why can't an external host initiate a connection to an internal host through PAT
  overload without a static translation?» — в таблице трансляций нет записи, пока
  внутренний хост первым не отправит исходящий пакет; входящий незапрошенный пакет
  роутеру не с чем сопоставить.

## Проверь себя

```check
?? Хост 192.168.1.10 выходит в интернет как 203.0.113.5. Как называется каждый из адресов?
!! 192.168.1.10 — inside local, 203.0.113.5 — inside global.
?? Чем PAT отличается от динамического NAT одним словом?
!! Ключевым словом overload: различение сессий по портам вместо отдельного адреса на хост.
?? Настроено правило NAT, трансляций нет. Что забыли?
!! Пометить интерфейсы командами ip nat inside и ip nat outside.
?? Что означает строка таблицы без указания протокола и портов?
!! Статическую трансляцию «один к одному».
?? Нужен ли NAT в IPv6 и что применяют вместо него?
!! Нет; для связи IPv6-клиента с IPv4-ресурсом применяют NAT64.
?? Одна из двух внутренних подсетей не выходит в интернет через PAT, хотя обе видны в таблице маршрутизации. Что проверить?
!! ACL, на который ссылается правило ip nat inside source list — покрывает ли он обе подсети; NAT транслирует только то, что разрешено этим списком.
?? Show ip nat statistics показывает Pool allocated 100% и растущий счётчик misses. В чём решение — расширять пул?
!! Не обязательно: правильнее добавить overload и превратить NAT в PAT — тогда сессии различаются портами, и одного-двух адресов хватает на весь офис.
?? Общий PAT overload настроен для исходящего трафика. Появится ли в таблице трансляций запись для сервера, к которому никто изнутри не обращался, но который должен быть доступен снаружи?
!! Нет — запись создаётся только исходящим пакетом; для входящих соединений снаружи нужна отдельная статическая трансляция.
?? Почему нельзя просто настроить PAT и рассчитывать, что снаружи достучатся до любого внутреннего сервера?
!! Потому что таблица трансляций строится исходящими пакетами; входящий запрос без существующей записи роутеру не с чем сопоставить, и он его отбрасывает.
```
