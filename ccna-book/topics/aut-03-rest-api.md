## Что делает REST API «REST»

REST — архитектурный стиль поверх HTTP. Признаки, которые спрашивают:

- **Клиент-серверная модель** и **отсутствие состояния** (stateless): каждый запрос
  самодостаточен, сервер не помнит предыдущий. Отсюда — токен или учётные данные **в
  каждом** запросе.
- **Ресурсы адресуются URI**: `/dna/intent/api/v1/network-device/42`.
- **Единообразный интерфейс**: одни и те же методы HTTP для любых ресурсов.
- Данные обычно в **JSON**, реже в XML.
- Кэшируемость и слоистость архитектуры.

## Методы и CRUD

| Метод | CRUD | Что делает | Идемпотентен |
|---|---|---|---|
| **GET** | Read | получить | да |
| **POST** | Create | создать новый объект | **нет** |
| **PUT** | Update/Replace | заменить объект целиком | да |
| **PATCH** | Update | изменить часть полей | **нет** (по спецификации) |
| **DELETE** | Delete | удалить | да |

> [!key] Запомнить
> **Идемпотентность** — повторный одинаковый запрос не меняет результат. Пять раз PUT —
> объект в том же состоянии; пять раз POST — пять созданных объектов. На этом строится
> вопрос «какой метод безопасно повторить».

## Коды ответов

| Код | Класс | Значение |
|---:|---|---|
| **200** | 2xx — успех | OK, ответ в теле |
| **201** | | Created — объект создан |
| **204** | | No Content — успех, тела нет |
| **301/302** | 3xx | перенаправление |
| **400** | 4xx — ошибка клиента | Bad Request: тело или параметры неверны |
| **401** | | Unauthorized: **не аутентифицирован** |
| **403** | | Forbidden: аутентифицирован, но **прав не хватает** |
| **404** | | Not Found: ресурса нет |
| **429** | | Too Many Requests: превышен лимит |
| **500** | 5xx — ошибка сервера | Internal Server Error |

Разница **401 против 403** — любимая пара в вопросах: «кто ты, я не знаю» против «я знаю,
кто ты, и тебе нельзя».

## Как выглядит запрос

```txt
POST /dna/intent/api/v1/network-device HTTP/1.1
Host: sandbox.cisco.com
Content-Type: application/json
Accept: application/json
X-Auth-Token: eyJhbGciOiJIUzI1NiIsInR5cCI6...

{
  "ipAddress": ["10.10.20.85"],
  "snmpVersion": "v3",
  "userName": "netadmin"
}
```

Составные части, которые просят назвать:

- **метод** — что делаем;
- **URI/endpoint** — над чем;
- **заголовки** — `Content-Type` (в каком формате отправляем), `Accept` (в каком хотим
  получить), заголовок аутентификации;
- **тело (payload)** — данные, обычно JSON; у GET его нет.

## Аутентификация

| Способ | Как выглядит | Замечание |
|---|---|---|
| **Basic** | `Authorization: Basic base64(user:pass)` | base64 — не шифрование, только HTTPS |
| **Token / Bearer** | `X-Auth-Token: …` или `Authorization: Bearer …` | сначала логин, потом токен во всех запросах |
| **API key** | ключ в заголовке или параметре | просто, но ключ легко утекает |
| **OAuth 2.0** | обмен на access token | для интеграций между сервисами |

Типичный сценарий с контроллером Cisco: POST на `/api/system/v1/auth/token` с Basic-логином
→ в ответ токен → все дальнейшие запросы с этим токеном.

## REST рядом с NETCONF и RESTCONF

| | REST | RESTCONF | NETCONF |
|---|---|---|---|
| Транспорт | HTTP(S) | HTTP(S) | **SSH** (порт 830) |
| Формат | JSON/XML | JSON/XML | XML |
| Модель данных | произвольная | **YANG** | **YANG** |
| Операции | методы HTTP | методы HTTP | `<get-config>`, `<edit-config>`, `<commit>` |

RESTCONF — «REST-обёртка» над теми же YANG-моделями, что использует NETCONF; NETCONF
старше, умеет транзакции и откат конфигурации.

## Разбор: полный цикл CRUD на одном ресурсе

Скрипт создаёт VLAN через API контроллера, проверяет результат и затем удаляет её.

```txt
1. POST /api/v1/vlan   {"id": 50, "name": "GUEST"}
   → 201 Created, тело содержит созданный объект с его id

2. GET /api/v1/vlan/50
   → 200 OK, тело: {"id": 50, "name": "GUEST", "status": "active"}

3. PATCH /api/v1/vlan/50   {"name": "GUEST-WIFI"}
   → 200 OK, изменилось только поле name, остальное осталось прежним

4. DELETE /api/v1/vlan/50
   → 204 No Content, тела в ответе нет — подтверждение без данных

5. GET /api/v1/vlan/50   (повторно, после удаления)
   → 404 Not Found — ресурс больше не существует
```

Разбор кодов по шагам показывает, зачем их вообще различают: `201` (а не просто `200`)
на шаге 1 явно говорит, что объект **создан заново**, а не просто обработан; `204` на
шаге 4 — успех без содержимого, потому что после удаления возвращать нечего; `404` на
шаге 5 — не ошибка скрипта, а корректное подтверждение, что ресурса действительно больше
нет. Если бы шаг 1 повторили ещё раз с теми же данными, результатом стал бы **второй**
объект с новым id — это и есть неидемпотентность POST на практике, а не абстрактное
определение.

## Диагностика: API вдруг начал отвечать 401 посреди работы скрипта

**Симптом.** Скрипт успешно логинится, получает токен, делает несколько запросов подряд
— а через какое-то время (иногда через час) все следующие запросы с тем же токеном
начинают получать `401 Unauthorized`, хотя логика скрипта не менялась.

**Что смотрим.** Не токен как таковой, а его **срок действия**:

```txt
Ответ на логин:
{"token": "eyJhbGci...", "expiresIn": 3600}
```

**Что нашли.** Токен выдаётся с ограниченным временем жизни (`expiresIn: 3600` — час), и
по его истечении сервер закономерно отвечает `401`, как будто токена не было вовсе — с
точки зрения кода ответа недействительный токен неотличим от отсутствующего. Это не
поломка API, а ожидаемое поведение: долгоживущие скрипты обязаны либо переавторизоваться
заранее по таймеру, либо ловить именно `401` и запрашивать новый токен перед повтором
запроса, а не считать любую `401` фатальной ошибкой конфигурации.

> [!key] Запомнить
> `401` в середине долгой сессии работы со скриптом почти никогда не значит «неверные
> учётные данные с самого начала» — гораздо чаще это означает «токен истёк», и решение —
> повторный логин, а не поиск ошибки в изначальном запросе.

## Диагностика: PUT случайно стёр половину настроек объекта

**Симптом.** Скрипт обновил только один параметр устройства через `PUT`, а после этого
все остальные ранее заданные поля объекта сбросились на значения по умолчанию.

**Что смотрим.** Тело запроса, которое реально ушло на сервер:

```txt
PUT /api/v1/vlan/50
{"name": "GUEST-WIFI"}
```

**Что нашли.** `PUT` по определению **заменяет ресурс целиком** тем, что прислано в теле
— это и есть его семантика «replace», в отличие от `PATCH` («изменить часть»). Отправив
только поле `name`, скрипт фактически сказал серверу: «вот полное новое описание этого
объекта, и в нём есть только имя» — все поля, которых не было в теле запроса, считаются
не заданными и сбрасываются или удаляются, в зависимости от реализации API. Это тот же
принцип идемпотентности, что уже разбирался, только с обратной стороны: `PUT`
предсказуем и идемпотентен именно потому, что не пытается угадать намерение — он
безусловно заменяет. Правильный метод для частичного изменения — `PATCH`, а не `PUT` с
неполным телом.

## Что спрашивают

- «Which HTTP method creates a resource?» — POST.
- «Which method is idempotent?» — GET, PUT, DELETE (POST — нет).
- «What does 401 mean versus 403?» — не аутентифицирован против нет прав.
- «Which characteristic describes REST?» — stateless, ресурсы по URI, методы HTTP.
- «Which header specifies the format of the body?» — `Content-Type`.
- «Which protocol uses SSH port 830 and YANG?» — NETCONF.
- Разбор куска запроса: назвать метод, endpoint, тип аутентификации, формат данных.
- «What does a `204` response to a DELETE request mean?» — успех, но тела в ответе нет —
  после удаления возвращать нечего.
- «A long-running script starts receiving 401 responses after working correctly for an
  hour. What is the most likely cause?» — истёк срок действия токена; нужен повторный
  логин, а не поиск ошибки в исходном запросе.
- «A script sends `PUT` with only one field to update a single setting, and the rest of
  the object's fields reset to defaults. Why?» — PUT заменяет ресурс целиком присланным
  телом; для частичного изменения нужен PATCH, а не PUT с неполными данными.

## Проверь себя

```check
?? Какой метод HTTP соответствует операции Update целиком?
!! PUT (частичное изменение — PATCH).
?? Сервер вернул 403. Проблема в токене?
!! Нет: аутентификация прошла, не хватает прав. Отсутствие или недействительность токена дали бы 401.
?? Что означает stateless применительно к REST?
!! Сервер не хранит контекст между запросами — каждый запрос несёт всё необходимое, включая аутентификацию.
?? Зачем нужны заголовки Content-Type и Accept?
!! Первый сообщает формат отправляемого тела, второй — желаемый формат ответа.
?? Чем RESTCONF отличается от NETCONF?
!! Работает поверх HTTP(S) с методами HTTP и JSON/XML, тогда как NETCONF — поверх SSH с XML и собственными операциями.
?? POST с одним и тем же телом отправили дважды подряд. Что получится?
!! Два разных созданных объекта с разными id — POST не идемпотентен, каждый вызов создаёт новую запись.
?? Скрипт работал час, потом все запросы с тем же токеном стали получать 401. В чём вероятная причина?
!! Истёк срок действия токена (expiresIn) — нужен повторный логин за новым токеном, это не ошибка в исходных учётных данных.
?? PUT отправили с телом, содержащим только одно изменённое поле. Что произойдёт с остальными полями объекта?
!! Они будут сброшены — PUT заменяет ресурс целиком присланным телом; для изменения одного поля без потери остальных нужен PATCH.
```
