## Зачем сети рисуют слоями

Плоская сеть из десяти коммутаторов, включённых друг в друга как получилось, работает —
ровно до первого сбоя. Иерархия нужна не ради красоты: она делает так, что **отказ
предсказуем, а рост не требует переделки**. Каждому слою назначена ровно одна работа, и
устройство одного слоя не берёт на себя работу другого.

## Трёхуровневая (three-tier) архитектура

```txt
        [ Core ]  [ Core ]
          |  \      /  |
          |   \    /   |
      [ Dist ]      [ Dist ]
        |    \      /    |
   [Access][Access][Access]
      |       |        |
    PC/AP   PC/AP    PC/AP
```

| Слой | Работа | Чего там не делают |
|---|---|---|
| **Access** | подключение конечных устройств, PoE, VLAN, port security, PortFast | маршрутизации и фильтрации магистрального трафика |
| **Distribution** | агрегирование access-коммутаторов, inter-VLAN routing, ACL и QoS-политики, граница broadcast-доменов | подключения пользователей напрямую |
| **Core** | быстрая коммутация между блоками distribution, максимальная доступность | тяжёлых политик, ACL, NAT — всё, что тормозит |

Правило, которое проверяют вопросами: **политика — на distribution, скорость — на core,
пользователи — на access**. Access-коммутаторы никогда не соединяют друг с другом
напрямую в этой модели; каждый идёт двумя аплинками в два distribution-коммутатора.

## Двухуровневая (collapsed core)

Если площадка одна и блоков distribution всего один-два, отдельный core становится
лишними коробками: distribution и core «схлопывают» в один слой — отсюда название
**collapsed core**.

- Дешевле: меньше устройств, меньше портов, меньше лицензий.
- Логика та же: access внизу, объединённый слой сверху.
- Предел применимости — когда блоков distribution становится больше трёх-четырёх:
  соединять их между собой полной сеткой дороже, чем поставить core.

## Spine-leaf

Классическая иерархия строилась под трафик **north-south** — от пользователя к серверу и
в интернет. В дата-центре трафик стал **east-west**: виртуальные машины и микросервисы
разговаривают между собой куда больше, чем с внешним миром. Дерево с корнем для этого плохо
подходит — путь между двумя серверами может подниматься до core и спускаться обратно.

```txt
   [Spine]   [Spine]   [Spine]
     |  \  /   |  \  /   |
     |   X     |   X     |
   [Leaf]   [Leaf]   [Leaf]
     |         |        |
  серверы   серверы  серверы
```

Свойства, которые спрашивают:

- **Каждый leaf соединён с каждым spine**; leaf с leaf и spine со spine — никогда.
- Путь между любыми двумя серверами всегда одинаковый: leaf → spine → leaf. Отсюда
  предсказуемая задержка (**два хопа всегда**).
- Расширение по полосе — добавить spine; расширение по портам — добавить leaf.
- STP в такой фабрике не используется: работает L3 между leaf и spine (ECMP) либо
  overlay (VXLAN), поэтому все линки активны одновременно.

## Почему уровней именно три

За иерархией стоит арифметика отказов и путей.

**Каждый access-коммутатор подключён двумя аплинками в два разных
distribution-коммутатора.** Отсюда:

- отказ одного аплинка или одного distribution не отрезает этаж;
- путей всегда два, значит переключение — это работа STP или маршрутизации, а не выезд
  инженера;
- количество линков растёт линейно с числом access-коммутаторов, а не квадратично, как
  было бы при «каждый с каждым».

Блок «access + пара distribution» называют **building block** или **switch block**. Сеть
растёт добавлением блоков, и это ключевое свойство: новый корпус не заставляет
переделывать существующие.

```txt
   Core ──────────────┬──────────────
        │             │
  ┌─────┴─────┐  ┌────┴──────┐
  │ Dist  Dist│  │ Dist  Dist│      ← блок = пара distribution
  │  ╲    ╱   │  │  ╲    ╱   │
  │  Access   │  │  Access   │
  └───────────┘  └───────────┘
     корпус A       корпус B
```

Core нужен, когда блоков становится больше трёх-четырёх: соединять их попарно дороже, чем
подключить каждый к паре core-коммутаторов.

### Где проходит граница L2 и L3

Два варианта дизайна, которые различают в вопросах:

| | L2 access (классика) | Routed access |
|---|---|---|
| VLAN пользователей | тянутся до distribution | заканчиваются на access-коммутаторе |
| Что работает между access и distribution | транк + STP | маршрутизация (OSPF/EIGRP) |
| Сходимость при отказе | секунды (RSTP) | доли секунды (IGP) |
| Роуминг VLAN между этажами | возможен | невозможен |
| Сложность | ниже | выше, нужен L3 на каждом access |

В классическом дизайне **distribution — граница broadcast-домена**: там живут SVI, шлюзы
по умолчанию и FHRP (HSRP/VRRP), там же применяются ACL. В routed access граница
поднимается на сам access-коммутатор.

> [!key] Запомнить
> «Где настраивают шлюз по умолчанию для пользовательской VLAN» в трёхуровневой сети —
> на **distribution**, обычно как виртуальный адрес FHRP на паре коммутаторов.

## Физические топологии

| Топология | Как выглядит | Где встречается |
|---|---|---|
| **Star (звезда)** | все узлы к одному центру | почти любая современная LAN |
| **Full mesh** | каждый с каждым, `n(n−1)/2` линков | ядро WAN, где нужна максимальная отказоустойчивость |
| **Partial mesh** | ключевые узлы связаны напрямую, остальные — нет | типичный WAN-компромисс цена/отказоустойчивость |
| **Hub-and-spoke** | филиалы только с центром | WAN с центральным ЦОД, дёшево, но центр — единая точка отказа |
| **Ring (кольцо)** | по кругу | городские оптические сети, metro Ethernet |
| **Bus (шина)** | общий сегмент | только в истории, коаксиал 10BASE2 |

Число линков для full mesh считают формулой `n(n−1)/2` — вопрос «сколько каналов нужно
для полной сетки из 6 маршрутизаторов» решается в уме: 6·5/2 = 15.

## WAN, SOHO и филиалы

**WAN** соединяет площадки, разнесённые географически, и почти всегда арендуется у
провайдера:

- **Leased line** (выделенная линия) — постоянная точка-точка, своя полоса, дорого.
- **MPLS L3VPN** — провайдер участвует в маршрутизации, площадки видят друг друга как
  соседей.
- **Metro Ethernet** — Ethernet как услуга внутри города.
- **Broadband + VPN over Internet** — дёшево, полоса не гарантирована; поверх него строят
  IPsec-туннели или SD-WAN.
- **Сотовая связь (LTE/5G)** — обычно резерв основного канала.

**SOHO** (small office / home office) — сеть на одно помещение: один комбинированный
роутер с встроенным коммутатором, точкой доступа, DHCP-сервером, NAT и firewall. Всё то
же самое, что в кампусе, но в одной коробке и без резервирования. Экзамен любит
подчёркивать: в SOHO **одно устройство совмещает роли**, а в кампусе роли разнесены.

## Как считают отказоустойчивость и полосу

Три величины, которые встречаются в вопросах про дизайн.

**Число линков полной сетки.** `n(n−1)/2`. Для 4 узлов — 6, для 6 — 15, для 10 — 45.
Именно поэтому full mesh делают только там, где узлов единицы.

**Переподписка (oversubscription).** Отношение суммарной полосы «вниз» к полосе «вверх».
Access-коммутатор с 48 портами по 1 Гбит/с и двумя аплинками 10 Гбит/с даёт
48 : 20 ≈ **2,4 : 1**. Для кампуса нормой считают до 20 : 1 на access и до 4 : 1 на
distribution; в ЦОД стремятся к 3 : 1 и лучше. Вывод, который спрашивают: аплинки обязаны
быть быстрее пользовательских портов, иначе узкое место переезжает в дизайн.

**Точки отказа.** Дизайн проверяют вопросом «что перестанет работать, если убрать этот
элемент». В правильной схеме нет элемента, чей отказ отрезает целый корпус: пара
distribution, два аплинка, два маршрута наружу, два питания.

### Спарка distribution: как избавляются от STP

Пару distribution-коммутаторов часто объединяют в один логический (**StackWise Virtual**,
VSS, vPC у других вендоров). Тогда два аплинка access-коммутатора собираются в один
**EtherChannel** к «одному» устройству: заблокированных портов нет, обе линии работают,
STP не участвует в переключении. Это стандартный ответ на «как задействовать оба аплинка
одновременно».

## WAN: чем соединяют площадки

| Технология | Полоса | Гарантии | Где применяют |
|---|---|---|---|
| Leased line (**T1** 1,544 Мбит/с, **E1** 2,048 Мбит/с, оптика) | фиксированная | жёсткие | критичные каналы, дорого |
| **MPLS L3VPN** | по договору | SLA, QoS от провайдера | корпоративные WAN |
| Metro Ethernet | 10 Мбит/с – 10 Гбит/с | SLA внутри города | площадки в одном городе |
| Broadband (DSL, кабель, GPON) | асимметричная | нет | филиалы, резерв |
| **VPN через интернет** | сколько даст канал | нет | дёшево, поверх любого доступа |
| LTE/5G | переменная | нет | резерв, временные площадки |
| Спутник | низкая, задержка 500+ мс | нет | удалённые объекты |

Что из этого спрашивают:

- **MPLS** — провайдер участвует в маршрутизации, площадки видят друг друга как соседей;
  клиенту не нужно строить туннели, но и контроля меньше.
- **VPN через интернет** — площадки соединяет сам клиент (IPsec), полоса не гарантирована.
- **Гибрид** — основной канал MPLS, резервный интернет; переключение по протоколу
  маршрутизации или SD-WAN-политикой.
- **SD-WAN** — поверх любых каналов, выбор пути по приложению, централизованная политика
  (см. главу про SDN).

Резервирование WAN считают так же, как в кампусе: два канала **разных технологий и разных
операторов**, иначе «два канала» одного провайдера падают одной аварией.

## On-premise и облако

| | On-premise | Облако |
|---|---|---|
| Где стоит железо | в вашем ЦОД | у провайдера |
| Кто обслуживает | вы | провайдер |
| Оплата | CapEx, покупка вперёд | OpEx, по потреблению |
| Скорость масштабирования | недели (закупка) | минуты |
| Контроль над данными | полный | ограничен договором |

Модели обслуживания:

- **IaaS** — вам дают виртуальную машину и сеть; ОС и всё выше — ваша забота.
- **PaaS** — вам дают среду выполнения; вы приносите только код.
- **SaaS** — вам дают готовое приложение (почта, CRM), вы управляете только учётками.

Модели развёртывания: **public**, **private**, **hybrid** (часть нагрузки внутри, часть
снаружи, между ними защищённый канал), **community**.

> [!key] Запомнить
> Гибридное облако требует связности: либо IPsec/VPN через интернет, либо выделенное
> подключение (Direct Connect / ExpressRoute). Это самый частый «правильный ответ» в
> вопросах про перенос части нагрузки в облако.

### Пять характеристик облака

Формулировки NIST, которые встречаются почти дословно:

1. **On-demand self-service** — ресурсы выделяются без обращения к человеку.
2. **Broad network access** — доступ по сети с любых устройств.
3. **Resource pooling** — общий пул ресурсов на многих клиентов.
4. **Rapid elasticity** — быстро вверх и вниз по нагрузке.
5. **Measured service** — потребление измеряется и оплачивается по факту.

Отсюда типичные преимущества в вариантах ответа: не нужно закупать железо заранее, платишь
за использованное, масштабирование за минуты. И типичные ограничения: зависимость от
канала до провайдера, вопросы размещения данных, стоимость исходящего трафика.

### Что меняется в сети при переезде в облако

- Трафик, который раньше не покидал ЦОД, теперь идёт через WAN — **канал наружу становится
  критичным**, ему нужен резерв и QoS.
- Появляется требование к **связности с облаком**: VPN или выделенное подключение.
- **DNS и аутентификация** становятся распределёнными: часть сервисов снаружи.
- Меняется точка применения политики: firewall на границе видит больше внутреннего
  трафика, чем раньше.

## SOHO: что внутри одной коробки

```txt
   [ Интернет ]
        │
   ┌────┴─────────────────────────┐
   │  SOHO-роутер                 │
   │  • NAT/PAT наружу            │
   │  • DHCP-сервер внутрь        │
   │  • простой firewall          │
   │  • Wi-Fi (точка доступа)     │
   │  • 4 порта коммутатора       │
   └────┬───────────────┬─────────┘
      PC/принтер     смартфоны
```

Что об этом спрашивают: одно устройство совмещает роли роутера, коммутатора, точки доступа,
DHCP-сервера и firewall; наружу все выходят под одним публичным адресом через PAT; резерва
нет ни по питанию, ни по каналу. Кампус отличается ровно тем, что каждая роль вынесена в
отдельное устройство и продублирована.

## Разбор задачи: сеть на три этажа

Условие, типичное для вопросов про дизайн: здание, три этажа, по 80 рабочих мест на этаже,
серверная в подвале, выход в интернет один, планируется рост.

**Что решаем по шагам.**

1. **Access.** На каждом этаже нужен коммутатор минимум на 96 портов с PoE (телефоны,
   точки доступа) — это два-три коммутатора в стеке. Порты пользователей: `switchport mode
   access`, PortFast, BPDU guard, port security.
2. **Аплинки.** От каждого этажного стека — **два** линка (лучше 10G) в два разных
   distribution-коммутатора в серверной. Собираются в EtherChannel, если пара
   distribution работает как одно логическое устройство.
3. **Distribution.** Пара L3-коммутаторов: SVI для каждой VLAN, FHRP как шлюз по
   умолчанию, ACL между сегментами, точка стыка с серверной фермой.
4. **Core.** На одно здание не нужен — это **collapsed core**. Появится, когда зданий
   станет три-четыре.
5. **Граница.** Роутер и firewall к провайдеру; второй канал другого оператора как резерв.
6. **Адресация.** По VLAN на функцию и этаж: данные, голос, Wi-Fi, управление, гости — и
   отдельная подсеть под каждую (см. главу про подсети).

**Чего в такой схеме быть не должно** — и это ровно то, что подсовывают в неверных
вариантах: один аплинк на этаж, пользователи, воткнутые в core, маршрутизация на
access-коммутаторе «потому что он умеет», VLAN, растянутая через всё здание без
необходимости, и гостевой Wi-Fi в той же VLAN, что бухгалтерия.

## Признак в вопросе → нужная архитектура

| Что сказано в условии | Ответ |
|---|---|
| «одна площадка, немного блоков, экономия» | collapsed core (two-tier) |
| «несколько зданий, много блоков распределения» | three-tier |
| «дата-центр, трафик между серверами, предсказуемая задержка» | spine-leaf |
| «филиалы соединяются с центральным офисом» | hub-and-spoke WAN |
| «каждая площадка должна иметь прямой путь к каждой» | full mesh (и считаем `n(n−1)/2`) |
| «домашний офис, одно устройство» | SOHO |
| «часть нагрузки у провайдера, часть у себя» | hybrid cloud + защищённое соединение |
| «оплата по потреблению, быстрое масштабирование» | облако, OpEx |
| «нужны оба аплинка активными» | EtherChannel к логически единой паре distribution |
| «сходимость доли секунды на access» | routed access (L3 до этажа) |

## Что спрашивают

- «Which two characteristics describe the access layer in a three-tier architecture?» —
  подключение конечных устройств, PoE, port security; **не** маршрутизация между
  distribution-блоками и не транзит трафика между зданиями.
- «What is the benefit of a collapsed core design?» — меньше устройств и стоимости для
  небольшой площадки при сохранении иерархии.
- «Which topology provides a predictable two-hop path in a data center?» — spine-leaf.
- «How many links are required for a full mesh of N routers?» — `N(N−1)/2`.
- Вопросы про SOHO обычно проверяют, что одно устройство выполняет функции роутера,
  коммутатора, точки доступа и firewall одновременно.
- Про облако чаще всего спрашивают разницу CapEx/OpEx и кто за что отвечает в IaaS/PaaS/SaaS.

## Проверь себя

```check
?? На каком слое трёхуровневой модели применяют ACL и inter-VLAN routing?
!! На distribution. Core оставляют максимально быстрым и без политик.
?? Почему в spine-leaf не нужен STP?
!! Между leaf и spine работает маршрутизация (ECMP) или overlay вроде VXLAN — петель L2 нет, все линки активны.
?? Сколько каналов нужно для полной сетки из 7 площадок?
!! 7·6/2 = 21.
?? Чем collapsed core отличается от three-tier?
!! Слои distribution и core объединены в один — это тот же дизайн для площадки, которой не нужен отдельный core.
?? Компания перенесла часть серверов к провайдеру, остальное осталось в своём ЦОД. Как называется модель и что нужно между частями?
!! Hybrid cloud; нужен защищённый канал — IPsec VPN или выделенное подключение.
?? Где в классическом трёхуровневом дизайне живёт шлюз по умолчанию пользовательской VLAN?
!! На distribution — обычно виртуальным адресом HSRP/VRRP на паре коммутаторов.
?? 48 портов по 1 Гбит/с и два аплинка по 10 Гбит/с. Какая переподписка?
!! 48 к 20, то есть примерно 2,4 : 1.
?? Чем routed access отличается от классического L2 access?
!! VLAN заканчиваются на самом access-коммутаторе, между ним и distribution работает маршрутизация — сходимость быстрее, но растянуть VLAN между этажами нельзя.
?? Два канала в интернет от одного провайдера — это резервирование?
!! Слабое: авария у оператора выключит оба; резерв делают разными операторами и по возможности разными технологиями.
?? Назови три из пяти признаков облака по NIST.
!! Самообслуживание по требованию, эластичность, измеряемое потребление (а также широкий сетевой доступ и общий пул ресурсов).
```
