## Зачем виртуализируют серверы

Физический сервер под одну задачу простаивает: процессор занят на единицы процентов,
память наполовину свободна, а место в стойке и питание оплачены целиком. Виртуализация
режет одну машину на много: **лучше утилизация, быстрее развёртывание, дешевле
резервирование и перенос нагрузки**.

## Гипервизор

Гипервизор — слой, который распределяет физические ресурсы между виртуальными машинами и
изолирует их друг от друга. Каждая ВМ видит «свой» процессор, память, диск и сетевую
карту.

| | Type 1 (bare-metal) | Type 2 (hosted) |
|---|---|---|
| Где работает | прямо на железе | поверх обычной ОС |
| Примеры | VMware ESXi, Hyper-V, KVM, Proxmox | VirtualBox, VMware Workstation |
| Накладные расходы | минимальные | выше (две ОС в стеке) |
| Где применяют | ЦОД, продуктив | лаборатория, ноутбук инженера |

> [!trap] Ловушка
> Гипервизор **не предоставляет операционную систему** виртуальной машине — ОС ставит
> администратор внутрь ВМ. Гипервизор выдаёт и контролирует **ресурсы**. Формулировку
> «controls and distributes physical resources for each virtual machine» надо узнавать.

Каждая ВМ обычно имеет собственную ОС, собственный IP-адрес и собственный виртуальный
MAC — с точки зрения сети это отдельный узел.

## Как ВМ попадает в сеть

Внутри гипервизора работает **виртуальный коммутатор** (vSwitch, Distributed Switch,
Open vSwitch). Виртуальные NIC машин включены в него, а физические NIC сервера служат
аплинками наружу.

```txt
      [ VM1 ] [ VM2 ] [ VM3 ]
         |       |       |
      ┌──────── vSwitch ────────┐
      │   VLAN 10   VLAN 20     │
      └─────── uplink NIC ──────┘
                  |
             физический
             коммутатор (trunk)
```

Практические следствия, которые спрашивают:

- Порт физического коммутатора, куда включён сервер, обычно настраивают **транком** —
  через него идут все VLAN виртуальных машин.
- Трафик между двумя ВМ на **одном** хосте физического коммутатора не покидает: он
  коммутируется внутри vSwitch. Поэтому его не видно в SPAN на физическом порту, а ACL на
  коммутаторе к нему неприменим.
- MAC-таблица физического коммутатора видит за одним портом **много MAC** — все ВМ хоста.
  Это норма, а не атака (см. главу про MAC-таблицу).

## Контейнеры

Контейнер — не «маленькая ВМ». Он использует **ядро ОС хоста** и изолирует только процессы
и файловую систему приложения.

| | Виртуальная машина | Контейнер |
|---|---|---|
| Что виртуализируется | железо | пространство имён ОС |
| Своя ОС внутри | да, полноценная | нет, общее ядро хоста |
| Размер | гигабайты | десятки-сотни мегабайт |
| Старт | десятки секунд | доли секунды |
| Изоляция | сильная | слабее, зависит от ядра |
| Типичный инструмент | ESXi, KVM | Docker, containerd, Kubernetes |

Оба подхода сосуществуют: контейнеры часто запускают внутри виртуальных машин.

## VRF

**VRF** (virtual routing and forwarding) — это несколько независимых таблиц маршрутизации
на одном роутере. Каждый интерфейс приписан к своему VRF, и таблицы друг о друге не знают.

Аналогия, которая помогает: **VLAN делит коммутатор на несколько логических коммутаторов,
VRF делит роутер на несколько логических роутеров**.

Зачем это нужно:

- разделить арендаторов, филиалы или контуры (продуктив/тест/гости) без покупки второго
  устройства;
- допустить **пересекающиеся адресные пространства**: 192.168.1.0/24 в двух VRF — это две
  разные сети, и они не конфликтуют;
- обеспечить изоляцию трафика на уровне маршрутизации, а не только фильтрацией.

```cfg
ip vrf CUSTOMER-A
!
interface GigabitEthernet0/1
 ip vrf forwarding CUSTOMER-A
 ip address 192.168.1.1 255.255.255.0
```

```cli
R1# show ip route vrf CUSTOMER-A
R1# ping vrf CUSTOMER-A 192.168.1.10
```

Обычная команда `show ip route` покажет только глобальную таблицу — маршруты VRF в ней не
видны. Это частая причина «маршрут пропал», а на деле смотрят не в ту таблицу.

## Диагностика: маршрут «пропал» после настройки VRF

**Симптом.** Администратор только что привязал интерфейс к VRF и настроил на нём
маршрутизацию, но `show ip route` больше не показывает ни сам интерфейс, ни его сети —
как будто конфигурация исчезла.

**Что смотрим.** Какую таблицу маршрутизации на самом деле спрашивают:

```cli
R1# show ip route
Gateway of last resort is not set
     10.0.0.0/24 is subnetted, 1 subnets
C       10.10.10.0 is directly connected, GigabitEthernet0/2

R1# show ip route vrf CUSTOMER-A
Routing Table: CUSTOMER-A
     192.168.1.0/24 is directly connected, GigabitEthernet0/1
```

**Что нашли.** Ничего не пропало — интерфейс `Gi0/1` привязан к VRF `CUSTOMER-A`
(`ip vrf forwarding CUSTOMER-A`), и с этого момента он живёт **в отдельной таблице
маршрутизации**, полностью изолированной от глобальной. Команда `show ip route` без
ключа `vrf` показывает только глобальную таблицу и намеренно не видит ничего, что относится
к другим VRF, — это не баг, а сама суть изоляции. Диагностировать такие случаи нужно не
«где потерялся маршрут», а «в какой таблице его теперь искать»: то же самое произойдёт с
`ping`, `traceroute` и большинством других команд — все они требуют ключа `vrf <имя>`,
если адрес находится не в глобальной таблице.

> [!trap] Ловушка
> Привязка интерфейса к VRF командой `ip vrf forwarding` **сбрасывает IP-адрес** на этом
> интерфейсе, если он был настроен раньше глобально — экзамен любит эту деталь в
> сценариях «после ip vrf forwarding интерфейс перестал пинговаться»: адрес нужно
> прописать заново уже после привязки к VRF.

## Диагностика: ВМ ненадолго теряет связь после миграции на другой хост

**Симптом.** После живой миграции виртуальной машины (vMotion, live migration) на другой
физический хост кластера она несколько секунд недоступна по сети, хотя сама ВМ работает.

**Что смотрим.** Что происходит с точки зрения физического коммутатора, когда ВМ меняет
хост, а вместе с ним — и физический порт, через который её трафик выходит наружу:

```cli
SW1# show mac address-table address 0050.7966.6800
Vlan    Mac Address       Type        Ports
----    -----------       --------    -----
  10    0050.7966.6800    DYNAMIC     Gi1/0/2   ! старый хост
```

**Что нашли.** MAC-адрес ВМ до миграции числится за портом старого хоста. После переезда
трафик к этому MAC продолжает идти на старый порт, пока коммутатор не увидит от ВМ новый
кадр с её же source MAC на **новом** порту и не перепишет запись — тот же самый механизм
обучения по source MAC, что и в главе про MAC-таблицу, только триггером выступает не
старение, а физическое перемещение адреса. Современные платформы виртуализации ускоряют
это, посылая **gratuitous ARP** от имени ВМ сразу после миграции — коммутатор учит новый
порт немедленно, а не ждёт следующего исходящего пакета от самой ВМ. Если такой ускоряющей
рассылки нет (отключена в настройках кластера), провал будет заметно дольше — вплоть до
обычных 300 секунд aging time, если ВМ на новом месте вообще ничего не передаёт первой.

## Сетевые режимы контейнера

Контейнер, в отличие от ВМ, не имеет собственного полноценного сетевого стека по
умолчанию — режим сети выбирают явно:

| Режим | Что видно снаружи | Типичное применение |
|---|---|---|
| **Bridge** | контейнер получает адрес во внутренней подсети хоста, наружу — через NAT и проброс портов | по умолчанию для одиночных контейнеров |
| **Host** | контейнер использует сетевой стек хоста напрямую, без изоляции портов | когда важна производительность, порты не должны конфликтовать |
| **None** | сетевого интерфейса нет вовсе | изолированные задачи без сети |
| **Overlay** | виртуальная сеть поверх нескольких хостов кластера | контейнеры одного приложения на разных узлах общаются напрямую |

Экзаменационный уровень детализации — не команды Docker, а сам факт: **сетевая изоляция
контейнера — программная настройка, а не физическое разделение**, в отличие от ВМ, у
которой всегда есть отдельный виртуальный NIC в vSwitch.

## Что спрашивают

- «Which role does a hypervisor provide for each virtual machine?» — выделяет и
  контролирует физические ресурсы, изолирует машины.
- «How do servers connect to the network in a virtual environment?» — через виртуальные
  NIC в виртуальный коммутатор, а тот — через физические аплинки хоста.
- «What is a benefit of server virtualization?» — утилизация железа, быстрое
  развёртывание, меньше физических серверов.
- «Which is true about containers?» — общее ядро с хостом, легче и быстрее ВМ, но слабее
  изоляция.
- «What is the purpose of a VRF?» — независимые таблицы маршрутизации на одном устройстве,
  в том числе с пересекающейся адресацией.
- «An interface is assigned to a VRF, but `show ip route` no longer shows its network.
  What is the most likely explanation?» — сеть не пропала, а находится в таблице
  маршрутизации этого VRF; нужно смотреть `show ip route vrf <имя>`.
- «After binding an interface to a VRF, connectivity fails. What should be checked?» —
  сохранился ли IP-адрес на интерфейсе: `ip vrf forwarding` сбрасывает ранее настроенный
  адрес, его нужно задать заново.
- «A VM is briefly unreachable immediately after a live migration to another host. Why?»
  — MAC-адрес ВМ ещё числится за портом старого хоста в таблице физического коммутатора,
  пока не придёт кадр (или gratuitous ARP) с нового порта.
- «What differentiates container network isolation from VM network isolation?» — у
  контейнера изоляция программная (настройка сетевого режима), у ВМ — всегда отдельный
  виртуальный NIC, подключённый к vSwitch.

```check
?? Чем контейнер принципиально отличается от виртуальной машины?
!! Он использует ядро ОС хоста и изолирует только приложение, поэтому легче и стартует мгновенно, но изолирован слабее.

!! Он коммутируется внутри виртуального коммутатора гипервизора и физический порт не покидает.
?? Как настроить порт коммутатора к хосту виртуализации с ВМ в разных VLAN?
!! Транком — иначе VLAN виртуальных машин не пройдут наружу.
?? Две разные сети внутри одного роутера используют 10.0.0.0/24 каждая. Как это возможно?
!! Они лежат в разных VRF — у каждого своя таблица маршрутизации, адреса не конфликтуют.
?? После ip vrf forwarding CUSTOMER-A на интерфейсе пропала связь, хотя раньше адрес был настроен. Что проверить в первую очередь?
!! Остался ли на интерфейсе IP-адрес — привязка к VRF сбрасывает ранее настроенный адрес, его нужно прописать заново.
?? Show ip route не показывает сеть, которую только что настроили на интерфейсе в VRF. Где искать эту сеть?
!! В таблице маршрутизации самого VRF: show ip route vrf <имя> — глобальная команда её никогда не покажет.
?? Виртуальная машина недоступна несколько секунд сразу после переезда на другой хост кластера, хотя сама работает. Почему?
!! Физический коммутатор ещё помнит её MAC за портом старого хоста; связь восстановится, как только придёт кадр (в идеале gratuitous ARP) с нового порта и запись переучится.
```
