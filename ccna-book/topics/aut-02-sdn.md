## Три плоскости

| Плоскость | Что делает | Примеры |
|---|---|---|
| **Data (forwarding) plane** | пересылает пакеты по уже готовым таблицам | ASIC коммутатора, FIB |
| **Control plane** | строит эти таблицы | OSPF, EIGRP, BGP, STP, ARP |
| **Management plane** | доступ к устройству и наблюдение | SSH, SNMP, syslog, NetFlow |

Идея SDN в одной фразе: **вынести control plane с устройств на контроллер**. Устройства
остаются быстрыми исполнителями, а решения принимаются централизованно, с полной картиной
сети.

## Северный и южный API

```txt
      приложения, скрипты, портал
                 ▲
         northbound API (REST)
                 │
          [  контроллер  ]
                 │
      southbound API (NETCONF, RESTCONF,
        OpenFlow, gRPC, Telnet/SSH)
                 ▼
        коммутаторы и роутеры
```

- **Northbound** — «наверх», к приложениям и людям. Обычно **REST API**: им пользуются
  скрипты, системы оркестрации, порталы самообслуживания.
- **Southbound** — «вниз», к устройствам: **NETCONF** (XML поверх SSH), **RESTCONF**
  (HTTP+JSON), **OpenFlow**, **gRPC/gNMI**, а в переходных решениях — обычные SSH-команды.

Направление легко запомнить по картинке: приложения сверху, железо снизу.

## Underlay и overlay

- **Underlay** — физическая сеть: коммутаторы, кабели, IP-адреса на линках и IGP, который
  обеспечивает связность между устройствами. Задача одна — чтобы любой узел мог достучаться
  до любого.
- **Overlay** — логическая сеть поверх него: туннели (**VXLAN**, GRE, IPsec), в которых
  живёт пользовательский трафик. Он не знает о физической топологии.
- **Fabric** — underlay и overlay вместе, управляемые как единое целое с общей политикой.

Преимущество разделения: политика («кто с кем может общаться») перестаёт зависеть от того,
куда воткнут кабель.

## SD-Access

Фабрика для кампуса, управляемая **Catalyst Center** (прежнее имя — DNA Center):

- **Control plane** — LISP: отдельная база «кто где находится» вместо флудинга.
- **Data plane** — VXLAN: пользовательский трафик инкапсулируется между fabric-узлами.
- **Политика** — SGT (Security Group Tags) через **TrustSec**: правила пишутся в терминах
  групп («гости», «медицина»), а не адресов и VLAN.
- Роли узлов: **edge** (к пользователям), **border** (выход из фабрики), **control plane
  node** (база соответствий).

Что это даёт на практике: сотрудник подключается где угодно и получает свою политику;
макросегментация делается VN (виртуальными сетями), микросегментация — тегами SGT.

## SD-WAN

То же разделение, но для филиалов через любые каналы (интернет, LTE, MPLS):

- **vManage** — управление и настройка;
- **vSmart** — контрольная плоскость, раздаёт политики и маршруты;
- **vBond** — знакомит устройства друг с другом при подключении;
- **vEdge/cEdge** — сами маршрутизаторы на площадках.

Ценность: **выбор канала по приложению** (голос в MPLS, резервные копии в интернет),
шифрование по умолчанию, единая политика на все филиалы, быстрое подключение новой
площадки (zero-touch provisioning).

## Что умеет контроллер кампуса

- инвентаризация: какие устройства есть, версии ПО, топология;
- шаблоны конфигураций и массовое применение;
- **assurance** — оценка «здоровья» клиентов и сети, поиск причин проблем;
- обновление ПО по расписанию;
- **северный REST API** — всё то же самое доступно скрипту.

## Разбор: путь одной команды через northbound и southbound API

Администратор через веб-портал Catalyst Center нажимает «создать новую VLAN 50 на всех
коммутаторах доступа кампуса».

```txt
1. Портал (northbound-клиент) отправляет REST-запрос контроллеру:
   POST /dna/intent/api/v1/... с телом JSON, описывающим VLAN 50
   (northbound API — обращение "сверху", от приложения к контроллеру)
2. Контроллер проверяет intent, разбивает задачу по устройствам, которых она касается
3. Контроллер обращается к каждому коммутатору southbound-протоколом
   (NETCONF/RESTCONF или, для старых платформ, обычным CLI поверх SSH)
4. Каждый коммутатор применяет конфигурацию локально и подтверждает результат
5. Контроллер собирает статусы со всех устройств и возвращает единый ответ порталу
```

Ключевая идея, которую это иллюстрирует: **администратор ни разу не заходит на конкретный
коммутатор** — вся связь идёт через контроллер, и именно поэтому SDN называют
**intent-based**: человек описывает *что* нужно получить (VLAN 50 везде), а не *как*
именно это сделать на каждой отдельной платформе с её синтаксисом. Традиционный подход
потребовал бы того же самого набора команд, введённых вручную (или скриптом) на каждом из
десятков коммутаторов по отдельности, без единой точки проверки результата.

## Диагностика: клиент в SD-Access не получает ожидаемую политику

**Симптом.** Сотрудник подключается к сети в новом здании кампуса, получает адрес, но
доступ к ресурсам не соответствует его группе — например, гостевое устройство получает
доступ к внутренним ресурсам.

**Что смотрим.** Соответствие между VN (виртуальной сетью, макросегментация) и SGT
(тегом группы, микросегментация) для этого порта на edge-узле:

```cli
EDGE1# show cts role-based sgt-map all
Active IPv4-SGT Bindings Information

IP Address              SGT     Source
10.10.50.20              10     LOCAL
```

**Что нашли.** Если устройству назначен SGT `10` (условно «Гости»), а политика TrustSec на
control plane node не содержит правил для этого тега — по умолчанию такой трафик может
либо получить излишний доступ (permit по умолчанию, пока политика не задана явно), либо,
наоборот, быть заблокирован там, где не должен. Диагностика в SD-Access разделяется на два
независимых уровня: **правильно ли устройство попало в SGT** (это происходит на edge-узле
при подключении — вручную, по порту или через 802.1X) и **что этот SGT разрешает**
(это уже политика на control plane node/ISE). Симптом «не тот доступ» может быть на любом
из двух уровней, и лечится по-разному — переназначением группы или правкой политики.

## Диагностика: филиал SD-WAN не получает маршруты и политику

**Симптом.** Новый маршрутизатор cEdge включили в филиале, он поднялся, но трафик через
него не идёт по ожидаемым политикам — как будто устройство не подключено к оверлею вовсе.

**Что смотрим.** Установил ли cEdge control-plane соединение с vSmart (не только
управляющее с vManage):

```cli
cEdge1# show control connections
PEER    PEER    SITE    PEER            
TYPE    STATE   ID      IP              
vsmart  down    100     10.0.0.20
vmanage up      -       10.0.0.10
```

**Что нашли.** Соединение с `vmanage` (только настройка и мониторинг) поднято, а с
`vsmart` (та самая control plane, которая раздаёт маршруты и политики оверлея) — нет. Это
разделение ролей и есть суть архитектуры: устройство может быть полностью управляемым
(видно в vManage, применяет конфигурацию), но без сессии с vSmart оно не получит ни
маршруты overlay, ни политики трафика — то есть формально «подключено», но не
полноценный участник фабрики. Причины разрыва именно этой сессии — обычно вопрос
связности к конкретному control-компоненту (порт, ACL, NAT-прохождение), а не общей
проблемы канала, раз vManage работает.

## Что спрашивают

- «Which plane forwards packets?» — data plane.
- «Which API type is used by applications to talk to a controller?» — northbound (REST).
- «Which protocols are southbound?» — NETCONF, RESTCONF, OpenFlow, gRPC.
- «What is the difference between underlay and overlay?» — физическая сеть против
  логической поверх неё.
- «Which technology encapsulates user traffic in SD-Access?» — VXLAN (control plane —
  LISP).
- «What is a benefit of controller-based networking?» — единая политика, полная видимость,
  быстрое развёртывание.
- «What does "intent-based networking" mean in practice?» — администратор описывает
  желаемый результат (intent) через northbound API, а контроллер сам транслирует его в
  southbound-команды для каждого затронутого устройства.
- «A guest device unexpectedly has access to internal resources in an SD-Access fabric.
  What are the two independent things to check?» — правильно ли устройству назначен SGT
  на edge-узле, и что именно этот SGT разрешает в политике TrustSec.
- «A cEdge router shows an active session with vManage but not with vSmart. What is the
  practical effect?» — устройство управляется и видно в системе, но не получает маршруты
  и политики overlay — оно не полноценный участник SD-WAN фабрики.
