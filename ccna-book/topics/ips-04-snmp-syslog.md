## SNMP: опрос устройств

Три роли:

- **Manager (NMS)** — система мониторинга, которая опрашивает.
- **Agent** — процесс на устройстве, который отвечает.
- **MIB** — база объектов агента; каждый параметр адресуется числовым **OID**.

Операции:

| Операция | Кто инициирует | Смысл |
|---|---|---|
| `get` / `getnext` / `getbulk` | manager | прочитать значение |
| `set` | manager | **изменить** параметр на устройстве |
| `trap` | agent | сообщить о событии самому, без опроса |
| `inform` | agent | то же, но с подтверждением от manager |

Порты: агент слушает **UDP 161**, manager принимает trap на **UDP 162**.

> [!key] Запомнить
> `trap` инициирует устройство, а не система мониторинга — на этом строятся вопросы «как
> NMS узнает об отказе интерфейса, не дожидаясь опроса». Разница с `inform` — только в
> подтверждении доставки.

## Версии

| Версия | Аутентификация | Шифрование |
|---|---|---|
| v1 | community string открытым текстом | нет |
| v2c | то же, плюс getbulk и inform | нет |
| **v3** | пользователи, HMAC | **да** (AES/DES) |

Community string в v1/v2c — фактически пароль, летящий в открытом виде; `RO` даёт чтение,
`RW` — запись. Отсюда правильные ответы на вопросы о безопасности: **использовать v3**, а
если v2c неизбежен — ограничивать ACL и никогда не оставлять `public`/`private`.

```cfg
! v2c — минимально допустимо только с ACL
access-list 10 permit 10.0.0.50
snmp-server community R3adOnly RO 10
snmp-server host 10.0.0.50 version 2c R3adOnly
snmp-server enable traps

! v3 — правильный вариант
snmp-server group MON v3 priv
snmp-server user nms MON v3 auth sha AuthPass priv aes 128 PrivPass
```

## Syslog: журнал событий

Формат строки IOS:

```txt
*Aug 19 09:14:31.204 AEST: %LINEPROTO-5-UPDOWN: Line protocol on
    Interface GigabitEthernet0/1, changed state to down
             │        │ │
             │        │ └─ мнемоника события
             │        └─── уровень серьёзности (severity)
             └──────────── источник (facility)
```

Восемь уровней, от 0 до 7. Меньше число — серьёзнее:

| Уровень | Имя | Что попадает |
|---:|---|---|
| 0 | Emergency | система неработоспособна |
| 1 | Alert | требуется немедленное вмешательство |
| 2 | Critical | критическое состояние (перегрев, отказ блока) |
| 3 | Error | ошибка (интерфейс в err-disabled) |
| 4 | Warning | предупреждение |
| 5 | **Notification** | нормальное значимое событие — смена состояния интерфейса |
| 6 | Informational | информационное |
| 7 | Debugging | вывод debug |

Мнемоника для порядка: **E**very **A**wesome **C**isco **E**ngineer **W**ill **N**eed
**I**ce cream **D**aily.

Настройка уровня означает «этот и всё серьёзнее»: `logging trap 4` отправит уровни 0–4.

```cfg
logging host 10.0.0.60
logging trap informational          ! уровни 0–6 на сервер
logging buffered 16384 debugging    ! локальный буфер
logging console warnings            ! на консоль только 0–4
service timestamps log datetime msec localtime show-timezone
```

```cli
R1# show logging
Syslog logging: enabled
    Console logging: level warnings
    Buffer logging: level debugging, 214 messages logged
    Trap logging: level informational, host 10.0.0.60
```

Порт syslog — **UDP 514**.

## Куда идут сообщения

| Назначение | Команда | Особенность |
|---|---|---|
| Консоль | `logging console` | видно только у консольной сессии |
| Сессия vty | `terminal monitor` | **включается в каждой сессии заново** |
| Локальный буфер | `logging buffered` | теряется при перезагрузке |
| Внешний сервер | `logging host` | единственный вариант для хранения и анализа |

Классический вопрос: «подключился по SSH и не вижу сообщений, которые видны на консоли» →
нужна команда `terminal monitor`.

## Разбор: полный SNMP-опрос от запроса до ответа

NMS хочет узнать состояние интерфейса `GigabitEthernet0/1` на роутере.

```txt
1. NMS отправляет GetRequest на UDP 161: "какое значение у OID
   1.3.6.1.2.1.2.2.1.8.<индекс интерфейса>" (это ifOperStatus — рабочее состояние интерфейса)
2. Агент на роутере ищет этот OID в своей MIB, находит текущее значение
3. Агент отвечает GetResponse: значение "1" (up) или "2" (down)
```

Если интерфейс упадёт **между** плановыми опросами NMS, узнать об этом мгновенно через
`get` невозможно — опрос происходит по расписанию (например, раз в 5 минут), и до
следующего цикла NMS ничего не знает. Именно для таких событий и существует `trap`: агент
сам, без запроса, отправляет короткое сообщение о конкретном событии в момент, когда оно
произошло, а не ждёт, пока его спросят. Отсюда прямой практический вывод, который
спрашивают: **опрос (polling) даёт полную картину, но с задержкой до следующего цикла;
trap даёт мгновенное уведомление, но только о том конкретном событии, для которого он
настроен** — обе модели используют вместе, не заменяя одну другой.

## Диагностика: NMS не получает trap, хотя SNMP настроен

**Симптом.** `snmp-server host` и `snmp-server enable traps` настроены на роутере,
`show snmp` показывает статистику отправленных пакетов, растущую со временем, но сама
система мониторинга не показывает ни одного события.

**Что смотрим.** Путь UDP-пакета с traps до NMS, включая любые ACL по дороге:

```cli
R1# show access-lists 100 | include 162
    20 deny udp any any eq 162
```

**Что нашли.** На пути между роутером и NMS стоит ACL, который **блокирует** UDP-порт 162
— тот самый, на который приходят traps. Роутер честно формирует и отправляет пакеты
(счётчик в `show snmp` растёт — с точки зрения устройства всё в порядке), но они не
доходят до места назначения. Это тот же паттерн, что уже разбирался для syslog и других
UDP-сервисов: отправитель не получает никакого сигнала о том, что получатель их не
увидел, — сообщения просто исчезают где-то по пути. Диагностика начинается не с
переконфигурации SNMP, а с проверки пути пакета: ACL, firewall, маршрут до адреса NMS.

## Диагностика: пользователь SNMPv3 не может пройти аутентификацию

**Симптом.** NMS настроен опрашивать устройство по SNMPv3 с указанными учётными данными,
но получает ошибку аутентификации при каждой попытке.

**Что смотрим.** Точное совпадение протоколов auth/priv между конфигурацией устройства и
настройками на стороне NMS:

```cli
R1# show running-config | include snmp-server user
snmp-server user nms MON v3 auth sha AuthPass priv aes 128 PrivPass
```

**Что нашли.** На устройстве пользователь настроен с `auth sha` (SHA) и `priv aes 128`.
Если на стороне NMS в профиле опроса указан, например, `auth md5` вместо `sha` —
несовпадение алгоритма хеширования ломает аутентификацию полностью, даже если сам пароль
(`AuthPass`) введён идентично. В отличие от v1/v2c, где единственный секрет — это community
string, у v3 согласуются сразу **несколько независимых параметров** (имя пользователя,
протокол аутентификации, пароль аутентификации, протокол шифрования, пароль шифрования) —
и несовпадение **любого** из них даёт одну и ту же неинформативную ошибку авторизации,
требуя построчной сверки конфигурации на обеих сторонах.

## Что спрашивают

- «Which SNMP operation is initiated by the agent?» — trap (или inform).
- «Which SNMP version provides encryption?» — v3.
- «What is the purpose of a community string?» — простая аутентификация в v1/v2c,
  открытым текстом.
- «Which syslog level corresponds to an interface changing state?» — 5, notification.
- «What does logging trap 4 send?» — уровни 0–4 включительно.
- «Which port does syslog / SNMP use?» — UDP 514 / UDP 161 (traps 162).
- «Why does an SSH session not show log messages?» — не выполнена `terminal monitor`.
- «Why can't polling alone provide instant notification of an interface failure?» — опрос
  идёт по расписанию, и о событии между циклами NMS узнает только на следующем опросе;
  для мгновенного уведомления нужен trap.
- «An SNMP counter on the router shows traps being sent, but the NMS never receives them.
  What should be checked?» — путь UDP-пакета до NMS: ACL или firewall, блокирующий порт
  162, — устройство не получает сигнала о недоставке.
- «An SNMPv3 user fails authentication even with the correct password. What else must
  match between the device and the NMS?» — протоколы аутентификации и шифрования (auth
  sha/md5, priv aes/des) — несовпадение любого из них ломает аутентификацию так же, как
  неверный пароль.
