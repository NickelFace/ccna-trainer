## Единственное правило

Роутер выбирает маршрут **не** по порядку строк в конфигурации и **не** по тому, кто
пришёл первым. Он выбирает по длине совпадающего префикса — «чем конкретнее, тем лучше».

Пример таблицы:

```cli
S     0.0.0.0/0        via 203.0.113.1
D     10.0.0.0/8       via 10.1.1.2
O     10.1.0.0/16      via 10.1.1.6
S     10.1.5.0/24      via 10.1.1.10
S     10.1.5.64/26     via 10.1.1.14
```

Куда пойдут пакеты:

| Назначение | Выбранный маршрут | Почему |
|---|---|---|
| 10.1.5.70 | `10.1.5.64/26` | самый длинный совпавший префикс |
| 10.1.5.200 | `10.1.5.0/24` | в /26 не входит (там только .64–.127) |
| 10.1.9.4 | `10.1.0.0/16` | не попал ни в один /24 |
| 10.9.0.1 | `10.0.0.0/8` | совпал только /8 |
| 8.8.8.8 | `0.0.0.0/0` | не совпало ничего конкретного |

> [!key] Запомнить
> Административная дистанция и метрика сравниваются **только среди маршрутов с одинаковым
> префиксом**. Сначала выбирается самая точная строка, и лишь потом — из нескольких таких
> строк лучшая по AD и метрике.

## Как проверить себя быстро

Возьми назначение и посчитай, входит ли оно в диапазон каждой строки:

`10.1.5.70` и строка `10.1.5.64/26`: магическое число 64, блок 64–127 → **входит**.
`10.1.5.200` и та же строка: 200 > 127 → **не входит**, спускаемся к /24.

Это ровно арифметика подсетей из первой главы про них — вся сложность вопросов «какой
маршрут выберет роутер» в этом.

## Балансировка equal-cost

Если два маршрута к одной сети имеют **одинаковый префикс, одинаковую AD и одинаковую
метрику**, роутер использует оба (по умолчанию до 4 путей, максимум зависит от платформы):

```cli
R1# show ip route 192.168.9.0
Routing entry for 192.168.9.0/24
  Known via "ospf 1", distance 110, metric 20
  Routing Descriptor Blocks:
  * 10.0.0.2, from 10.0.0.2, via GigabitEthernet0/1
      10.0.0.6, from 10.0.0.6, via GigabitEthernet0/2
```

Балансировка идёт **по потокам** (per-destination) при CEF — это значит, что один и тот же
поток стабильно идёт по одному пути, а разные потоки распределяются. Per-packet тоже
возможна, но вызывает переупорядочивание пакетов и почти не применяется.

EIGRP умеет ещё и **unequal-cost** балансировку через `variance` — единственный IGP с
такой возможностью; это встречается как отличительный факт про EIGRP.

## Рекурсивный поиск next hop

Статический маршрут можно задать тремя способами:

```cfg
ip route 192.168.5.0 255.255.255.0 10.1.1.2                     ! только next hop
ip route 192.168.5.0 255.255.255.0 GigabitEthernet0/1           ! только интерфейс
ip route 192.168.5.0 255.255.255.0 GigabitEthernet0/1 10.1.1.2  ! и то, и другое
```

При задании через next hop роутер обязан **рекурсивно** найти, как добраться до самого
`10.1.1.2` — то есть в таблице должен быть маршрут и до него. Если его нет, маршрут не
установится вовсе (`%Route not installed`). Это причина «прописал маршрут, а его нет в
таблице».

Задание только через интерфейс на многоточечных сетях (Ethernet) плохо работает: роутер
будет слать ARP-запрос на каждый адрес назначения (proxy ARP), что медленно и неочевидно.
Поэтому на Ethernet-линках рекомендуют указывать **интерфейс и next hop вместе**.

## Что происходит с кадром при пересылке

Уже разбиралось в главе про инкапсуляцию, но здесь это причина типовых ошибок:

1. Роутер снимает L2-заголовок.
2. Ищет маршрут по destination IP.
3. Уменьшает TTL, пересчитывает контрольную сумму.
4. Строит **новый** L2-заголовок: source MAC — свой исходящий интерфейс, destination MAC —
   next hop (узнаётся через ARP).
5. Отправляет.

Если ARP до next hop не разрешается (сосед недоступен), маршрут в таблице есть, а трафик
не идёт. `show ip arp` — следующее место после `show ip route`.

## Быстрая пересылка

- **Process switching** — каждый пакет обрабатывает CPU. Медленно, встречается как
  «худший вариант».
- **Fast switching** — первый пакет через CPU, остальные по кэшу.
- **CEF** (Cisco Express Forwarding) — заранее построенные FIB и таблица смежностей;
  включён по умолчанию, работает на скорости порта.

```cli
R1# show ip cef 192.168.5.10
192.168.5.0/24
  nexthop 10.1.1.2 GigabitEthernet0/1
```

## Разбор рекурсии на два уровня

Рекурсивный поиск не всегда разрешается за один шаг — иногда next hop сам достижим только
через другой next hop.

```cli
S    203.0.113.0/24  via 198.51.100.2
S    198.51.100.0/30 via 10.1.1.2
C    10.1.1.0/30     is directly connected, GigabitEthernet0/1
```

Чтобы установить первый маршрут (`203.0.113.0/24 via 198.51.100.2`), роутер должен
разрешить, как добраться до `198.51.100.2`. Прямого подключения к этой сети нет — есть
второй статический маршрут `198.51.100.0/30 via 10.1.1.2`. Значит, разрешаем уже его:
`10.1.1.2` лежит в сети `10.1.1.0/30`, которая **directly connected** — вот и конец
рекурсии. Итоговый путь для пакета к `203.0.113.5` — через `Gi0/1`, ARP на `10.1.1.2`.
Если убрать среднюю строку (`198.51.100.0/30`), у первого маршрута не останется способа
разрешить next hop, и он **исчезнет из таблицы целиком** — тот же симптом «прописал
маршрут, а его нет», только через два шага рекурсии вместо одного, что усложняет поиск
причины на практике.

## Диагностика: маршрутизатор внезапно грузит CPU на 100 %

**Симптом.** Пропускная способность канала не выбрана целиком, а CPU роутера стабильно
загружен, `show interfaces` показывает потери на исходящих портах.

**Что смотрим.** Какой путь пересылки реально используется:

```cli
R1# show cef state
CEF Status: RP instance state: enabled
IPv4 CEF Status: enabled

R1# show interfaces gi0/1 | include switch
  Input queue: 0/75/1234/0 (size/max/drops/flushes)
```

**Что нашли.** Растущий счётчик `flushes`/`drops` во входной очереди при включённом CEF
обычно означает, что часть трафика **не пересылается по CEF**, а «спускается» на медленный
путь — process switching. Типичные причины: включённое логирование ACL (`log` заставляет
CPU разобрать каждый совпавший пакет), некоторые функции NAT/QoS, туннели с фрагментацией,
либо просто отключённый по ошибке `ip cef` на интерфейсе. Экзаменационный вывод — иерархия
трёх путей пересылки не абстракция: **process switching объясняет реальную перегрузку CPU
на trafике, который в норме должен идти по аппаратно ускоренному CEF**.

> [!trap] Ловушка
> «Маршрут в таблице правильный, значит пересылка в порядке» — не обязательно: даже
> корректный маршрут может пересылаться медленным путём, если конкретный пакет или функция
> интерфейса вынуждает роутер спуститься с CEF на process switching.

## Разбор задачи: равное и неравное распределение по путям

Три ситуации, которые часто путают между собой:

| Ситуация | Что делает роутер |
|---|---|
| Два маршрута, одинаковые AD и метрика | equal-cost балансировка, до 4 путей по умолчанию |
| Два маршрута, одинаковая AD, разная метрика (не EIGRP) | используется только маршрут с меньшей метрикой, второй — резерв, но не в таблице |
| Два маршрута EIGRP, метрика отличается в пределах `variance` | unequal-cost балансировка — оба в таблице, трафика больше идёт по лучшему пути |

Один поток (одна пара src/dst IP при обычном CEF-хэшировании) всегда идёт по **одному** из
доступных путей целиком — увидеть, что «половина трафика от одного и того же хоста идёт
по одному линку, а половина по-другому», нельзя, и это не повод считать балансировку
сломанной: она балансирует между потоками, а не внутри одного.

## Что спрашивают

- «Which route does the router use to forward the packet?» — longest prefix match.
- «How does the router load balance across two equal paths?» — по потокам, при равных
  AD и метрике.
- «Why is the configured static route missing from the routing table?» — нет маршрута до
  next hop (рекурсия не разрешилась) или интерфейс down.
- «Which protocol supports unequal-cost load balancing?» — EIGRP (variance).
- «What does the router rewrite when forwarding?» — MAC-адреса и TTL, IP не трогает.
- «A static route depends on a next hop that is reachable only through another static
  route. What happens if the intermediate route is removed?» — первый маршрут тоже исчезнет
  из таблицы: рекурсивный поиск next hop больше не разрешается.
- «CPU utilization is high while traffic volume is unremarkable, and interface counters show
  drops. What should be checked?» — какой путь пересылки реально используется: не спущен ли
  трафик с CEF на process switching (логирование ACL, отключённый ip cef, специфичные
  функции NAT/QoS/туннелей).
- «Two routes have equal AD but different metrics from the same protocol. What is
  installed?» — только маршрут с меньшей метрикой; равной метрики для балансировки нет.

?? Статический маршрут настроен, но в show ip route его нет. Первая причина?

?? Два маршрута OSPF к одной сети с метрикой 20 каждый. Что сделает роутер?

?? Один и тот же хост непрерывно шлёт трафик через equal-cost балансировку на два линка. Половина пакетов этого потока пойдёт по одному линку, половина — по другому?
