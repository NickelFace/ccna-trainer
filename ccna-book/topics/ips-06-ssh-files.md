## SSH: настройка по шагам

```cfg
hostname R1
ip domain-name example.com
crypto key generate rsa modulus 2048
ip ssh version 2
username admin privilege 15 secret S3cret!
!
line vty 0 15
 transport input ssh
 login local
```

Порядок не случаен: имя ключа строится из **hostname + domain-name**, поэтому без первых
двух команд третья не выполнится. Всё это подробно разбирается и в главе про доступ к
устройству — здесь важно, что этот же набор спрашивают и как часть домена IP-сервисов.

Проверка: `show ip ssh` (версия и длина ключа), `show ssh` (активные сессии).

## TFTP и FTP

| | TFTP | FTP |
|---|---|---|
| Транспорт | **UDP 69** | TCP 20/21 |
| Аутентификация | нет | логин и пароль |
| Возможности | только чтение и запись файла | листинг каталога, переименование, удаление, докачка |
| Надёжность | реализована внутри протокола, примитивно | обеспечивает TCP |
| Где применяют | загрузка образов и конфигураций устройства | обмен файлами общего назначения |

Из-за простоты TFTP влезает в загрузчик устройства — им пользуются при восстановлении, но
для повседневных задач он неудобен и небезопасен.

**SCP** — копирование поверх SSH; предпочтительный вариант там, где важна безопасность.

## Работа с конфигурациями

Два конфига, и их путают:

- **running-config** — в оперативной памяти, действует прямо сейчас, при перезагрузке
  теряется.
- **startup-config** — в NVRAM, загружается при старте.

```cli
R1# copy running-config startup-config     ! сохранить (то же самое, что write memory)
R1# copy running-config tftp:              ! резервная копия на сервер
Address or name of remote host []? 10.0.0.70
Destination filename [r1-confg]? r1-backup

R1# copy tftp: running-config              ! восстановить (СЛИЯНИЕ, не замена!)
R1# copy startup-config running-config     ! то же слияние
```

> [!trap] Ловушка
> `copy tftp: running-config` **сливает** файл с текущей конфигурацией: команды из файла
> добавляются, но то, чего в файле нет, не удаляется. Чтобы получить ровно ту
> конфигурацию, что в файле, копируют в **startup-config** и перезагружаются.

Сброс: `erase startup-config` (или `write erase`) + `reload`.

## Образы IOS

```cli
R1# show flash:
-#- --length-- -----date/time------ path
  1  108312884 Aug 12 2026 10:22:14 c2900-universalk9-mz.SPA.157-3.M.bin

R1# copy tftp: flash:                       ! залить новый образ
R1# verify /md5 flash:c2900-...bin          ! проверить целостность
R1(config)# boot system flash:c2900-universalk9-mz.SPA.157-3.M.bin
R1# show version                            ! какой образ загружен и откуда
```

Перед заливкой смотрят свободное место (`show flash:`), после — проверяют контрольную
сумму и только затем указывают `boot system` и перезагружаются.

## Порядок загрузки устройства

1. **POST** — самопроверка оборудования.
2. **Bootstrap** из ROM.
3. Поиск IOS: по командам `boot system` → первый образ во flash → TFTP → ROMmon.
4. Поиск конфигурации: **startup-config** в NVRAM → если её нет, запускается диалог
   первоначальной настройки (setup mode).

Значение **configuration register** `0x2102` — нормальная загрузка; `0x2142` — пропустить
startup-config, чем и пользуются при восстановлении забытого пароля.

## Разбор задачи: почему «восстановленный» конфиг не совпал с резервной копией

Администратор случайно удалил несколько ACL и VLAN, решил откатиться к вчерашней
резервной копии:

```cli
R1# copy tftp: running-config
Address or name of remote host []? 10.0.0.70
Source filename []? r1-backup
Destination filename [running-config]?
```

После выполнения удалённые ACL и VLAN **не восстановились**, а старые записи, которые
администратор успел добавить сегодня и которых не было во вчерашнем файле, **остались на
месте**. Причина — уже разобранное поведение `copy ... running-config`: команда **не
заменяет** текущую конфигурацию, а **добавляет** к ней содержимое файла построчно. Если
вчера ACL существовал, а сегодня его удалили командой `no access-list ...`, во вчерашнем
файле резервной копии по-прежнему записано `access-list ...` (положительное определение),
но слияние с running-config не содержит команды **отмены удаления** — оно просто
переиспользует то, что написано в файле, а того, чего там нет (например, явного «удалить
всё лишнее»), тоже нет. Правильная процедура полного отката:

```cli
R1# copy tftp: startup-config
R1# reload
```

Копирование в **startup-config** с последующей перезагрузкой гарантированно даёт
устройство именно в том состоянии, которое записано в файле, — потому что при загрузке
running-config строится **с нуля** из startup-config, а не сливается с чем-то уже
существующим.

## Диагностика: копирование на TFTP-сервер зависает или обрывается

**Симптом.** `copy running-config tftp:` запрашивает адрес и имя файла, но дальше вывод
останавливается на строке с точками (`!!!...`) и в итоге завершается ошибкой таймаута.

**Что смотрим.** Базовую связность до сервера — TFTP использует UDP и не сообщает
подробностей об ошибке так, как это делает TCP-based FTP:

```cli
R1# ping 10.0.0.70
Success rate is 0 percent (0/5)
```

**Что нашли.** Сервер недоступен на уровне L3 — либо неверно введён адрес, либо сам
TFTP-сервер выключен, либо между роутером и сервером нет маршрута. Поскольку TFTP работает
через **UDP без установления соединения**, роутер не получает от сети явного «отказано» —
он просто повторяет попытки, пока не истечёт таймаут, и в выводе это выглядит как
зависание, а не как мгновенная ошибка (сравни с TCP-соединением, где недоступный порт
сразу вернул бы RST — тема главы про TCP/UDP). Если `ping` проходит, а копирование всё
равно не удаётся — следующим проверяют, не запущена ли служба TFTP на сервере вообще
(в отличие от SSH/FTP, у TFTP часто нет постоянно висящей службы, её нужно включать
отдельно на время операции) и правильность имени файла.

## Диагностика: устройство после обновления IOS загружается в ROMMON

**Симптом.** Залили новый образ IOS во flash, прописали `boot system`, перезагрузили
устройство — вместо обычной загрузки оно оказывается в приглашении `rommon 1>`.

**Что смотрим.** Целостность и присутствие самого образа в загрузочном списке:

```cli
rommon 1> dir flash:
   108312884  c2900-universalk9-mz.SPA.157-3.M.bin

R1# show bootvar
BOOT variable = flash:c2900-universalk9-mz.SPA.158-3.M.bin,12   ! опечатка в версии
```

**Что нашли.** Переменная загрузки указывает на файл `...158-3.M.bin`, а во flash реально
лежит `...157-3.M.bin` — опечатка (или недокачанный файл) в команде `boot system`. Устройство
честно пытается найти именно тот файл, что прописан, не находит его и, не имея других
источников загрузки IOS, падает в ROMMON как в последний рубеж. Ровно поэтому в разделе
«Образы IOS» после копирования рекомендуют `verify /md5` — не только проверить, что файл
не повреждён при передаче, но и что имя в `boot system` совпадает с реальным именем файла
**посимвольно**. Восстановление — либо исправить `boot system` на верное имя и
перезагрузиться, либо (если образа во flash действительно нет или он повреждён) залить
IOS прямо из ROMMON через `tftpdnld`, если платформа это поддерживает.

## Что спрашивают

- «Which protocol uses UDP port 69?» — TFTP.
- «Which two capabilities does FTP have that TFTP lacks?» — аутентификация и работа с
  каталогами (листинг, удаление, переименование).
- «Which command backs up the configuration to a server?» — `copy running-config tftp:`.
- «What happens when a file is copied to running-config?» — слияние, а не замена.
- «Which command shows the IOS image in use?» — `show version`.
- «Where is startup-config stored?» — в NVRAM.
- «An administrator copies a backup file to running-config to undo unwanted changes, but
  deleted ACLs do not reappear. Why?» — команда слила файл с текущей конфигурацией, а не
  заменила её; для точного отката нужно копировать в startup-config и перезагружаться.
- «A `copy` to a TFTP server hangs and eventually times out instead of failing
  immediately. Why does this differ from a failed FTP transfer?» — TFTP работает поверх
  UDP без установления соединения, поэтому недоступный сервер не возвращает мгновенного
  отказа, только истечение таймаута повторных попыток.
- «A device boots into ROMMON after an IOS upgrade. What is a likely cause?» — `boot
  system` указывает на имя файла, которого нет во flash (опечатка или незавершённая
  копия) — устройству не на что опереться при загрузке.
