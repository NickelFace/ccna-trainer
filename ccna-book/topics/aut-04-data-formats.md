## Зачем форматы данных

Программы обмениваются структурами, а не текстом для человека. Формат задаёт правила
записи, чтобы обе стороны понимали одно и то же. На экзамене нужен один — **JSON** — и
общее представление о двух других.

## JSON: всё из четырёх элементов

```json
{
  "hostname": "R1",
  "uptime": 48213,
  "reachable": true,
  "location": null,
  "interfaces": [
    { "name": "GigabitEthernet0/0", "ip": "10.1.1.1", "enabled": true },
    { "name": "GigabitEthernet0/1", "ip": "10.1.2.1", "enabled": false }
  ]
}
```

| Элемент | Синтаксис | Пример |
|---|---|---|
| **Объект** | `{ }` — пары «ключ: значение» | `{"name": "R1"}` |
| **Массив** | `[ ]` — упорядоченный список | `["a", "b"]` |
| **Строка** | всегда в **двойных** кавычках | `"R1"` |
| **Число / логическое / null** | без кавычек | `48213`, `true`, `null` |

Правила, на которых ловят:

- Ключ всегда строка в двойных кавычках. `{name: "R1"}` — **невалидный** JSON (это
  JavaScript).
- Одинарные кавычки не допускаются.
- **Запятая после последнего элемента запрещена**.
- Комментариев в JSON нет.
- Значения `true`/`false`/`null` пишутся строчными и без кавычек; `"true"` — это строка.

## Как читать вложенность

Типовой вопрос: «сколько объектов внутри массива» или «какое значение у ключа X».
Алгоритм — смотреть на скобки:

```json
{
  "devices": [
    { "id": 1, "tags": ["core", "primary"] },
    { "id": 2, "tags": [] }
  ]
}
```

- Внешний `{ }` — один объект с единственным ключом `devices`.
- Его значение — **массив** из **двух** объектов.
- У первого объекта ключ `tags` содержит массив из двух строк, у второго — пустой массив.

Обращение по пути: `devices[0].tags[1]` = `"primary"`.

## XML

```xml
<device>
  <hostname>R1</hostname>
  <interfaces>
    <interface enabled="true">
      <name>GigabitEthernet0/0</name>
      <ip>10.1.1.1</ip>
    </interface>
  </interfaces>
</device>
```

Структура задаётся парными тегами, у элементов бывают **атрибуты**. XML многословнее
JSON, но именно он используется в **NETCONF** и описывается схемами. Требование одно:
каждый открытый тег обязан быть закрыт, документ имеет один корневой элемент.

## YAML

```yaml
hostname: R1
uptime: 48213
reachable: true
interfaces:
  - name: GigabitEthernet0/0
    ip: 10.1.1.1
    enabled: true
  - name: GigabitEthernet0/1
    ip: 10.1.2.1
    enabled: false
```

- Структура задаётся **отступами пробелами** — табуляции запрещены.
- Элемент списка начинается с `- `.
- Кавычки почти не нужны, комментарии — через `#`.
- YAML является надмножеством JSON: любой JSON — валидный YAML.

Поэтому YAML выбирают там, где файл пишет и читает человек: playbook Ansible, описание
инфраструктуры, конвейеры CI.

## Сравнение

| | JSON | XML | YAML |
|---|---|---|---|
| Читаемость человеком | средняя | низкая | высокая |
| Объём | компактный | многословный | самый компактный |
| Комментарии | нет | да | да |
| Где встречается | REST API, RESTCONF | NETCONF, SOAP | Ansible, конфигурации, CI |

## Разбор задачи: путь по вложенности до конкретного значения

Ответ RESTCONF на запрос состояния коммутатора:

```json
{
  "switch": {
    "hostname": "SW1",
    "vlans": [
      { "id": 10, "name": "SALES", "ports": ["Gi1/0/1", "Gi1/0/2"] },
      { "id": 20, "name": "VOICE", "ports": [] }
    ],
    "uplinks": {
      "primary": { "interface": "Gi1/0/24", "status": "up" },
      "backup": { "interface": "Gi1/0/25", "status": "down" }
    }
  }
}
```

Вопрос: «какой порт второй в списке портов VLAN с id 10?» Разбор по скобкам сверху вниз:

```txt
switch                      → объект
  .vlans                    → массив из двух объектов
    [0]                     → первый объект массива, id: 10 — это он
      .ports                → массив строк
        [1]                 → второй элемент (индексация с нуля!) = "Gi1/0/2"
```

Путь целиком: `switch.vlans[0].ports[1]` = `"Gi1/0/2"`. Второй частый вопрос того же вида
— «в каком состоянии backup-аплинк»: `switch.uplinks.backup.status` = `"down"`, и здесь
уже не массив, а вложенный **объект** внутри объекта — обращение по ключу, а не по
индексу. Различать эти два случая (числовой индекс в `[ ]` для массива, именованный ключ
через точку для объекта) — вся суть чтения вложенности в подобных вопросах.

> [!trap] Ловушка
> Индексация массивов в JSON (и в большинстве языков программирования, включая Python)
> начинается **с нуля**. «Второй элемент списка» — это индекс `1`, не `2`. Экзамен
> регулярно проверяет именно эту привычку считать с единицы.

## Разбор: пять сломанных фрагментов и что в них не так

```json
1. {name: "R1"}                        // ключ без кавычек — невалидно
2. {"name": 'R1'}                      // одинарные кавычки у значения — невалидно
3. {"name": "R1",}                     // запятая после последнего элемента — невалидно
4. {"enabled": "true"}                 // "true" в кавычках — валидно, но это СТРОКА, не логическое значение
5. {"tags": ["core", "primary",]}      // запятая после последнего элемента массива — невалидно
```

Строка 4 — намеренная ловушка другого рода: сам JSON синтаксически **валиден**, ошибка не
в синтаксисе, а в типе значения. Вопрос «is this valid JSON» про строку 4 должен получить
ответ «да», а вопрос «what type is the value of enabled» — ответ «строка, не boolean»: это
разные вопросы с разными правильными ответами про один и тот же фрагмент, и экзамен любит
предлагать оба варианта как отвлекающие для второго.

## Разбор: одни и те же данные в трёх форматах

Полезно один раз увидеть параллельно, что действительно отличается, а что нет:

```json
{"router": {"hostname": "R1", "interfaces": 2}}
```

```xml
<router>
  <hostname>R1</hostname>
  <interfaces>2</interfaces>
</router>
```

```yaml
router:
  hostname: R1
  interfaces: 2
```

Структура (объект `router` с двумя полями) одна и та же — различается только
**представление**. JSON и YAML эквивалентны почти буква в букву (YAML — это, по сути,
JSON без скобок и кавычек, со структурой через отступы); XML требует парного тега на
каждый элемент, из-за чего многословнее, зато позволяет использовать **атрибуты**
(`<interface enabled="true">`) — то, чего нет ни в JSON, ни в YAML в чистом виде. Это и
есть содержательный ответ на вопрос «почему в NETCONF используют XML, а не JSON» — не
исторический случай, а то, что YANG-модели, на которых строится NETCONF, изначально
проектировались со схемами и атрибутами в духе XML.

## Что спрашивают

- «Which JSON snippet is valid?» — проверить кавычки у ключей, лишние запятые, скобки.
- «How many objects are in this array?» — посчитать `{ }` внутри `[ ]`.
- «Which data format uses indentation?» — YAML.
- «What is the value of key X in this payload?» — пройти по вложенности.
- «Which format does NETCONF use?» — XML.
- Drag-and-drop: сопоставить фрагменты синтаксиса с их названиями (объект, массив, пара
  ключ-значение).
- «Given a nested JSON payload, what is the second element of an array field?» — элемент
  с индексом 1, а не 2 — индексация начинается с нуля.
- «Is `{"enabled": "true"}` valid JSON, and what type is its value?» — синтаксически
  валиден, но значение — строка, а не логический тип, из-за кавычек.
- «Why does NETCONF use XML instead of JSON?» — YANG-модели, на которых строится NETCONF,
  спроектированы со схемами и атрибутами в духе XML, которых нет в JSON и YAML.

## Проверь себя

```check
?? Валиден ли JSON {'name': 'R1'}?
!! Нет: в JSON строки и ключи пишутся только в двойных кавычках.
?? Как в JSON отличить массив от объекта?
!! Массив в квадратных скобках и упорядочен; объект в фигурных и состоит из пар «ключ: значение».
?? Что означает "enabled": false — строку или логическое значение?
!! Логическое: без кавычек это true/false, а "false" в кавычках было бы строкой.
?? Почему в YAML нельзя использовать табуляцию?
!! Структуру задают отступы пробелами; табуляция запрещена спецификацией и ломает разбор.
?? Какой формат используется в NETCONF?
!! XML.
?? В массиве "ports": ["Gi1/0/1", "Gi1/0/2"] нужен второй элемент. Какой у него индекс?
!! 1 — индексация массивов начинается с нуля, поэтому «второй элемент» это индекс 1, а не 2.
?? {"enabled": "true"} — валидный JSON? Что означает значение true в кавычках?
!! Да, синтаксически валиден; но "true" в кавычках — это строка, а не логическое значение, что часто и есть суть вопроса.
?? Почему в switch.uplinks.backup.status обращение идёт через точку и имя ключа, а не через числовой индекс?
!! Потому что uplinks — объект с именованными полями (primary, backup), а не массив; индекс в квадратных скобках нужен только для элементов массива.
```
