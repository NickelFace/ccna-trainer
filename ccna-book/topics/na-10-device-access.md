## Два способа добраться до устройства

- **Out-of-band** — доступ, не зависящий от работоспособности сети: консольный порт, AUX
  с модемом, service port контроллера, терминальный сервер. Работает, даже когда
  конфигурация сломана и IP-связности нет.
- **In-band** — доступ по самой сети: SSH, Telnet, HTTPS, SNMP. Удобно, но если сеть
  легла, сюда не попасть.

Отсюда правило, которое проверяют: **первичная настройка и восстановление — только через
консоль**; повседневная работа — по SSH.

## Консоль

Кабель rollover (RJ-45 или USB), параметры терминала: **9600 бод, 8 бит данных, без
контроля чётности, 1 стоп-бит, без управления потоком** (8-N-1). Их спрашивают набором.

```cfg
line console 0
 password cisco
 login
 exec-timeout 5 0
 logging synchronous
```

`logging synchronous` — чтобы сообщения журнала не рвали набираемую строку;
`exec-timeout 5 0` — выкидывать бездействующую сессию через 5 минут.

## Telnet и SSH

| | Telnet | SSH |
|---|---|---|
| Порт | TCP 23 | TCP 22 |
| Шифрование | **нет**, пароль летит открытым текстом | да |
| Аутентификация | пароль линии или локальный пользователь | обязательно имя пользователя |
| Где допустим | лаборатория | везде |

Настройка SSH — последовательность, которую любят разбирать по шагам:

```cfg
hostname SW1                                   ! 1. имя
ip domain-name example.com                     ! 2. домен — из hostname+domain строится имя ключа
crypto key generate rsa modulus 2048           ! 3. ключи (минимум 768, практически 2048)
ip ssh version 2                               ! 4. только вторая версия
username admin privilege 15 secret S3cret!     ! 5. локальный пользователь
!
line vty 0 15
 transport input ssh                           ! 6. никакого Telnet
 login local                                   ! 7. проверять по локальной базе
 exec-timeout 10 0
```

Без пунктов 1–2 команда генерации ключей не отработает: устройству нужно полное доменное
имя. `transport input ssh` — то самое место, где закрывают Telnet; вариант
`transport input all` в вопросах на безопасность всегда неверный.

## Линии vty

`line vty 0 15` — шестнадцать одновременных сессий удалённого доступа. Что с ними делают:

- ограничивают доступ ACL: `access-class 10 in` — заходить можно только с адресов
  управления;
- задают тайм-аут бездействия;
- включают `login local` (учётки) вместо общего пароля линии.

```cli
SW1# show users
    Line       User       Host(s)              Idle       Location
   0 con 0                idle                 00:00:00
*  2 vty 0     admin      idle                 00:00:00   10.0.99.55

SW1# show ssh
Connection Version Mode Encryption  Hmac   State         Username
0          2.0     IN   aes256-ctr  sha1   Session started  admin
```

## Веб-доступ и облако

- **HTTP (80)** — открытый текст, выключают: `no ip http server`.
- **HTTPS (443)** — оставляют, если нужен веб-интерфейс: `ip http secure-server`.
- **Cloud-managed** (Meraki, Catalyst Center/DNA Center) — устройство само поднимает
  туннель к облаку, администратор работает через портал. Плюс: не нужен доступ снаружи
  внутрь. Минус: зависимость от связи с облаком.

На контроллере беспроводной сети та же логика, только команда другая:
`config network webmode enable` открывает HTTP, а именно включение **HTTPS**
(`config network secureweb enable`) заставляет WLC самостоятельно сгенерировать локальный
самоподписанный SSL-сертификат для веб-администрирования — сертификат появляется не сам по
себе, а как побочный эффект включения именно защищённого протокола. У Telnet и Cisco WLC
есть и собственные ограничения управления: одновременных Telnet-сессий разрешено не больше
**пяти**, что регулярно спрашивают как отдельный числовой факт.

## Что нужно, чтобы удалённый доступ вообще был

1. У устройства есть IP: у роутера — на интерфейсе, у L2-коммутатора — на **SVI**.
2. Задан шлюз по умолчанию (`ip default-gateway` для L2-коммутатора).
3. Порт/VLAN управления активны.
4. Настроены аутентификация и `transport input`.
5. Пароль на привилегированный режим: `enable secret` (хешируется), не `enable password`.

Типовая цепочка отказов в вопросах: пингуется, но SSH не пускает → нет пользователя или
`login local`; не пингуется вовсе → SVI/шлюз/VLAN.

> [!trap] Ловушка
> `service password-encryption` шифрует пароли в конфиге **слабым** обратимым алгоритмом
> (тип 7) — это защита от взгляда через плечо, а не от атакующего. Настоящая защита —
> `enable secret` и `username … secret` (хеш).

## Диагностика: коммутатор пингуется, SSH просит логин и отказывает

**Симптом.** `ping` до management-адреса коммутатора проходит, SSH-клиент подключается,
показывает приглашение, но после ввода логина и пароля пишет `Access denied` или сразу
рвёт сессию.

**Что смотрим.** Порядок аутентификации, который реально настроен на vty:

```cli
SW1# show running-config | section line vty
line vty 0 4
 transport input ssh
 login
line vty 5 15
 transport input ssh
 login local
```

**Что нашли.** Сессии `vty 0 4` и `vty 5 15` — это **разные диапазоны с разными
настройками**, и это частая, но незаметная на глаз ошибка конфигурации. На первых пяти
линиях стоит просто `login` (проверка по паролю линии, а не по пользователю) без заданного
`password` — с точки зрения SSH-клиента это выглядит как «логин спросили, но принять
некому». На `vty 5 15` всё в порядке — `login local` сверяет введённые данные с локальной
базой пользователей. Диагноз ставится сравнением **обоих** диапазонов vty, а не только
того, куда «случайно» попала первая же сессия: до 16 одновременных линий могут быть
настроены по-разному, и симптом «то пускает, то нет» почти всегда означает именно это.

> [!trap] Ловушка
> Совпадающий на первый взгляд `transport input ssh` на обоих диапазонах не гарантирует
> одинаковое поведение — метод аутентификации (`login` против `login local`) настраивается
> отдельной строкой и может отличаться между диапазонами vty на одном устройстве.

## Диагностика: SVI поднят, а управления по сети всё равно нет

**Симптом.** На L2-коммутаторе настроен `interface vlan 10` с адресом, интерфейс в
состоянии `up/up`, но зайти на коммутатор по SSH ни с одного хоста не получается.

**Что смотрим.** Путь пакета от хоста к SVI — тот же набор проверок, что и для любого IP
на L3-устройстве, только здесь легко забыть про специфику L2-коммутатора:

```cli
SW1# show ip default-gateway
No default gateway is set
```

**Что нашли.** У L2-коммутатора (в отличие от роутера) нет полноценной таблицы
маршрутизации — есть только один-единственный **шлюз по умолчанию**
(`ip default-gateway`), который отвечает за весь трафик управления за пределы локальной
подсети. Если он не задан, SVI прекрасно отвечает на пинг из своей же подсети, но ни один
запрос из другой подсети до него не доберётся — ответу некуда идти. Это специфическая для
L2-коммутатора ловушка: на роутере или L3-коммутаторе тот же симптом означало бы проверку
полноценной таблицы маршрутизации, а здесь всё решается одной командой.

```cfg
ip default-gateway 10.10.10.1
```

Второй частый вариант той же истории — SVI поднят, но VLAN 10 **не включена в allowed
list** транка между коммутатором и остальной сетью управления: тогда трафик до SVI не
доходит уже на L2, ещё раньше диагностики самого IP.

## Диагностика: забыт пароль привилегированного режима

**Симптом.** Нужно попасть в привилегированный режим для восстановления доступа, но
`enable secret` неизвестен, а физический доступ к устройству есть.

**Что смотрим и делаем.** Процедура восстановления пароля через ROMMON — стандартная
последовательность, которую спрашивают по шагам, а не только результатом:

1. Перезагрузить устройство и прервать загрузку (обычно `Ctrl+Break` или удержание кнопки
   Mode на коммутаторе) до загрузки IOS — попасть в **ROMMON**.
2. Изменить регистр конфигурации так, чтобы стартовая конфигурация **не загружалась**:
   `confreg 0x2142`, затем `reset`.
3. Устройство загружается с пустой конфигурацией. Скопировать сохранённую конфигурацию
   из NVRAM в running: `copy startup-config running-config`.
4. Задать новый `enable secret`, вернуть регистр обратно (`config-register 0x2102`),
   сохранить и перезагрузить уже штатно.

**Что нашли.** Смысл шага 2 не «сбросить пароль», а **пропустить чтение startup-config**
при загрузке — именно поэтому на шаге 3 конфигурацию приходится копировать вручную, иначе
все остальные настройки (VLAN, порты, ACL) будут потеряны, а не только пароль. Частый
неверный вариант в вопросах — «просто перезагрузить устройство»: это никак не поможет,
пароль хранится в NVRAM и переживает обычную перезагрузку без изменения регистра.

> [!key] Запомнить
> Восстановление пароля требует **физического доступа к консоли** — это ещё один довод в
> пользу того, что консоль всегда должна быть физически защищена (в шкафу под замком), а не
> только паролем в конфигурации.

## Что спрашивают

- «Which method provides out-of-band access?» — консоль (или service port / AUX-модем).
- «Which commands are required to enable SSH?» — hostname, ip domain-name, crypto key
  generate rsa, username, transport input ssh, login local.
- «Why is Telnet not recommended?» — данные и пароли передаются открытым текстом.
- «What restricts which addresses may open a vty session?» — `access-class` на линии vty.
- «What is the default console speed?» — 9600 бод, 8-N-1.
- «Which command hashes the privileged-mode password?» — `enable secret`.
- «SSH works on some vty lines but not others on the same switch. What should be checked?»
  — настройки аутентификации (`login` против `login local`) могут отличаться между
  диапазонами линий vty, даже если `transport input` совпадает.
- «An SVI is up/up but a Layer 2 switch cannot be managed from another subnet. What is
  missing?» — `ip default-gateway` — у L2-коммутатора нет таблицы маршрутизации, только
  один шлюз по умолчанию для всего трафика управления.
- «What is the purpose of changing the configuration register to 0x2142 during password
  recovery?» — пропустить загрузку startup-config при старте, чтобы попасть в систему без
  пароля и без старой конфигурации.
- «Why must the configuration be copied from NVRAM to running-config during password
  recovery?» — при загрузке с изменённым регистром прочитанная конфигурация не
  применяется автоматически; без этого шага будут потеряны не только пароль, но и все
  остальные настройки.

?? Каких двух команд не хватит для генерации ключей SSH, если их не задать заранее?
!! hostname и ip domain-name — из них строится имя ключа.

!! transport input ssh.
?? Чем enable secret лучше enable password?
!! Он хранится в виде хеша, а password — в открытом виде (или под обратимым шифрованием типа 7).
?? Устройство пингуется, но SSH не пускает. Две вероятные причины?
!! Нет локального пользователя или не задан login local; либо на vty стоит transport input, не включающий ssh.
